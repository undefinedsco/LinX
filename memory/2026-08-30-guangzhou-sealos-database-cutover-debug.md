# Guangzhou Sealos database deployment debug

## Debug report

- **Symptom:** Guangzhou `undefineds` initially used native Kubernetes PostgreSQL/Redis objects, so the resources were not visible in the Sealos Database module. AI Gateway also failed to start after the managed-database cutover, first with a write-permission error and then with `prisma.engine.errors.NotConnectedError`.
- **Root cause:** Sealos Database discovers KubeBlocks `Cluster` resources rather than arbitrary StatefulSets/Deployments. AI Gateway's Guangzhou manifest additionally forced UID/GID `65532`; the published image writes `/app/runtime/litellm.generated.yaml` and launches Prisma under its image-default runtime contract. A temporary writable-volume workaround changed that contract and caused the Prisma query-engine health check to disconnect. Raising memory proved the failure was not an OOM condition.
- **Fix:** Created managed `undefineds-gz-postgresql` and `undefineds-gz-redis` resources in workspace `ns-iknkxtc8`, created isolated `ai_gateway`, `xpod_cloud`, and `xpod_rc` databases/roles, and routed Guangzhou Xpod/AI Gateway secrets to them. AI Gateway was aligned with the proven Singapore container startup contract and temporarily raised to a 4 GiB memory limit. After the user clarified that this is an additive deployment, the Guangzhou native `redis`, `xpod-rdf-postgres`, service aliases, and 20 GiB PVC structure were restored; the empty restored PostgreSQL was reinitialized with the required roles, databases, and extensions. Singapore was only queried read-only and was not modified.
- **Evidence:** Managed PostgreSQL and Redis both report `Running`; AI Gateway readiness returns HTTP 200 with `db=connected` and stayed Ready with zero restarts during repeated checks. Guangzhou LinX, ID, Xpod status, and ChatKit health URLs all return HTTP 200. Restored native Redis returns `PONG`; restored PostgreSQL, both service aliases, and its 20 GiB PVC are Ready/Bound. Singapore Redis, PostgreSQL, Xpod Cloud/RC, and AI Gateway remain Ready with their original creation timestamps.
- **Operational boundary:** The restored Guangzhou native PostgreSQL PVC is a new empty volume because the prior Guangzhou volume was deleted before the additive-only clarification. Service structure and schemas are restored, but deleted historical contents cannot be reconstructed from Kubernetes. The active Guangzhou business services continue to use the new managed databases, so native and managed resources now coexist.
- **Status:** DONE_WITH_CONCERNS — deployment and health verification are complete. Follow-up hardening should make the AI Gateway image write to a non-root-owned runtime directory, restore restricted pod security, and then reduce the temporary 4 GiB limit based on observed steady-state usage (about 970 MiB during verification).
