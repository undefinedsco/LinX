# Guangzhou QLever RC and discovery critical-path audit

## Debug report

- **Symptom:** Guangzhou exposes disabled `xpod-qlever-rc` and `discovery` workloads, raising the question whether the LinX/Xpod deployment is incomplete or missing critical services.
- **Root cause:** These are separate optional deployment lanes, not directories required by the current public Cloud runtime. `xpod-qlever-rc` is a private enterprise/QLever release-candidate acceptance stack that mounts `cloud.enterprise.json` and replaces the public SPARQL evaluator with native QLever. The active `xpod-cloud` and `xpod-rc` use `config/cloud.json`, whose public contract is `PostgresRdfEngine` plus `RdfQuerySparqlEngine`/Comunica. The standalone `discovery` service is an older remote metadata-sync service; current LinX reads the published `@undefineds.co/models` catalog and the live Xpod `/v1/models` route, with the published catalog as fallback.
- **Critical-path result:** Neither disabled Service is referenced by the active Gateway, LinX, Xpod Cloud/RC, Inngest, or AI Gateway runtime. The only `xpod-qlever-rc` string in active pod specs is a shared image-pull Secret name, not a network or runtime dependency. Guangzhou does not publish a discovery Ingress.
- **Evidence:** Both stacks remain at zero replicas while LinX `/chat`, Xpod account UI, Cloud service status, Cloud ChatKit health, and RC service status return HTTP 200. The three QLever-specific hostnames return 503 because their dedicated ingress points to a zero-endpoint Service; this failure is isolated from the main domains. Xpod source history explicitly keeps public Cloud independent of native QLever, and `docs/cli-app-shared-core.md` defines discovery as optional with an embedded fallback.
- **Fix:** No deployment change is required for the current Chat/Xpod path. Enable the QLever RC stack only for private native-SPARQL acceptance or enterprise promotion. Enable standalone discovery only if the product chooses server-managed provider/model recommendation synchronization instead of the current published/live fallback contract.
- **Related:** The managed PostgreSQL path currently logs that native `xpod_rdf` is unavailable and keeps RDF3X/public evaluation active. That is a capability choice, not a missing dependency for Chat, login, files, or ordinary Cloud SPARQL.
- **Status:** DONE — dependency tracing, live isolation checks, source contracts, and deployment references agree that neither disabled stack is on the current critical path.
