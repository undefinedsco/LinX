LinX 产品设计走查（自顶向下）

从产品定位出发，逐层对照 DESIGN.md 契约：产品叙事 → 信息架构 → 布局结构 → 模块形态 → 视觉气质。所有判断附真实截图证据（生产版 = 本地 xpod Pod 真实登录后走查；prototype = 设计意图参照）。

§0 总评：框架方向正确，坍塌在"产品叙事落地"

层级状态核心判断
产品层
首屏叙事		✗登录后第一眼是完全空白：无 Secretary welcome、无 composer、无存储/runtime 状态。chat-first 与"状态显式"两大产品承诺在首屏同时缺席。
框架层
信息架构		✓做得最好的一层：rail 四模块 + 设置菜单、Inbox 收敛为铃铛异常中心、keys/models 收进设置——与 DESIGN.md IA 一致。缺"当前空间/工作现场"的全局可见性。
布局层
结构契约		⚠两栏纪律与 48px head 统一；但 Files 布局与契约相反（常驻树占据 list pane）、无面包屑/返回、空态不 actionable、compact 破损。
模块层
形态差距		⚠settings / inbox 完整；files / contacts 半成品；chat 与 prototype 设计意图差距最大——设计是清楚的，生产没跟上。
气质层
视觉纪律		✓生产版整体符合 macOS-native 克制气质（中性面、稀疏紫、border-led）。断裂点：死按钮外露、原始 URL/ID 外露、登录跳转 xpod 营销页。

Layer 1 · Product

§1 产品层：用户第一眼理解到的，不是产品想传达的

DESIGN.md 的产品承诺：chat 是主舞台；Secretary 是不可变第一会话与首次入口；信任信号（存储位置 / provider / runtime / 审批状态）在使用点显式可见；"Useful before persistence settles"——本地确定性 UI 先于远端就绪。

坍塌

P1 · 登录后首屏 = 完全空白：无 welcome、无 composer、无任何"能做什么"

契约 · Empty Secretary thread shows the product welcome and starter actions above an available composer

真实走查：种子 Pod 登录成功 → 落在 /chat → 列表里有"LinX 主理人"会话 → 内容区整片空白。点击进入会话后依然空白（等待 6s+）。没有 Secretary welcome、没有输入框、没有错误说明、没有"去配置 AI Key"的引导。

根因（代码证据）：ChatContentPane.tsx:846 的 isStagedSecretaryWelcome = isSecretary && !activeThread —— welcome 只在"无选中 thread"时渲染；但 :856-870 的 effect 会自动选中第一个 thread，于是路径变成 ChatKitPanel，而 ChatKit 在无 runtime/AI key 时渲染为空白。welcome 被自己绕过了。

生产版 · 登录后首屏（18-web-home-chat.png）

列表有 Secretary（"暂无消息"），内容区空白。用户第一次打开产品，看到的是"什么都没有"。

设计意图 · prototype chat（01-chat-default.png）

设计意图是清楚的：welcome 卡（工作现场就绪）、审批卡（批准/拒绝/查看 Inbox）、右侧"当前工作现场 + Agent 能力 + 快捷入口"、底部 composer。设计没有缺失，是生产没落地。

坍塌

P2 · 信任信号在主路径全程缺席："我的数据在哪"无从得知

契约 · Trust signals: storage location, provider, runtime readiness… explicit at the point where the user needs them

走查全程（chat / contacts / files / favorites 四个主模块），界面上没有任何位置显示：当前存储空间（本机/云端）、Pod 地址、runtime 是否就绪、数据是否已同步。唯一的状态信号藏在"设置 → 运行环境"里的两个徽标（Web / Solid Pod 登录）——而信任信号契约要求它出现在用户需要它的使用点，不是低频设置页。

对比 prototype：chat 头部有"当前 Thread · 默认助手 · Pod 已同步"，右侧栏有"当前工作现场 Thread/Workspace/Repository"。生产版头部只有"Assistant › linx–lite"。

偏差

P3 · Secretary 身份叙事分裂：同一对象三个名字

契约 · Secretary is a product-owned fixed conversation: render it first, select it on first entry
  • 会话列表：LinX 主理人
  • 内容头部（未选中）：Assistant
  • 内容头部（选中后）：LinX 主理人 › linx–lite（linx–lite 是模型名，出现在面包屑层级里）
  • 联系人详情：LinX 主理人，ID 显示 __secretary__

用户无法建立"Secretary = 我的默认助手"这一核心心智。DESIGN.md 术语契约要求产品内统一 Secretary 叙事（prototype 统一为 "AI Secretary · 默认 Agent · 不可删除"）。

偏差

P4 · 登录路径气质断裂：克制弹窗 → xpod 营销页

LinX 登录弹窗是克制的产品语言（"数据保存位置 / 云端空间 / 本机空间"）；点"继续"后跳到 xpod OIDC 页——"Simplify Life with Your AI Secretary" 营销大字 + 紫色 SaaS 风。这恰好是 DESIGN.md Avoid 清单里的风格。虽然该页面属于 xpod 运行时，但用户把它当作 LinX 产品体验的一部分。

LinX 登录弹窗 · 克制、操作式（11-web-providers.png）

符合 spec：紧凑、无高级配置、数据位置前置。

xpod OIDC 页 · 营销风（14-web-oidc.png）

"Personal Messages Platform" 定位语与 LinX 也不一致。建议：自定义该页面（xpod 支持静态资源定制），至少改为操作式文案与中性视觉。

Layer 2 · Information Architecture

§2 框架层：收敛正确，是做得最好的一层

DESIGN.md IA 契约：Chat 主舞台；Contacts/Files/Favorites 支撑面；Inbox 是异常中心而非主 app；audit/keys/models/diagnostics 进 settings；Files 在 rail 只出现一次。

符合

IA1 · 全局导航：rail 四模块 + 设置菜单，与契约一致

  • rail：聊天 / 联系人 / 文件 / 收藏 + 底部设置菜单（通用设置 / 模型服务 / 服务管理 / 关于 / 退出登录）——PrimaryLayout.tsx:56 primaryNavIds = ['chat','contacts','files','favorites']，模型服务收进设置菜单 ✓
  • Inbox：不占 rail，以头部铃铛 + 弹层存在（统一收件箱：全部/待处理/审计 + 打开收件箱）——符合 "exception center, not a competing main app" ✓
  • Files 只出现一次 ✓；默认模块 chat ✓
  • prototype 曾把"聊天文件 / 聊天记录管理 / 密钥 / 模型"都放上 rail（9 个入口），生产版已收敛——这正是 DESIGN.md "Prefer fewer visible modules" 的正面实践。
生产版 · Inbox 铃铛弹层（20-web-inbox.png）

全局异常中心的正确形态：就地可见数量、可进入完整收件箱。

生产版 · 设置承载低频面（22-web-settings.png）

通用 / 版本更新 / 运行环境 / 本地网络——低频配置正确地藏进设置。

缺口

IA2 · "当前空间 / 工作现场"在框架层没有位置

框架没有任何全局槽位呈现"当前存储空间 + 工作现场"。prototype 的解法是 chat 右侧栏（当前工作现场：Thread / Workspace / Repository）；生产版 useChatLayoutConfig 有 rightSidebar 能力但 showRightSidebar 默认 false，且非 chat 模块没有等价物。建议：把"空间徽标"提升为框架级元素（如 rail 头像旁 / 内容头部左侧），而不是某个模块的侧栏内容——它是跨模块信任信号，不是 chat 的局部信息。

外露

IA3 · 调试/测试页面注册在生产路由表，任何用户可直接访问

router.tsx 中注册了 /debug/search-select、/debug/chat、/inrupt-test、/test/solid-ui-react、/test/inrupt-simple、/app/demo 等调试与试验页面。它们不在任何导航里，但通过 URL 直接可达——与 IA 收敛"fewer visible modules"同原则：调试面不应存在于生产构建。建议：按 import.meta.env.DEV 条件注册，或集中到 /debug/* 并在生产构建中剔除。

Layer 3 · Layout

§3 布局层：统一的两栏纪律做对了，Files 的结构与契约相反

契约：全应用统一 rail + list + content；48px head；Files 恰好两个常驻 pane（当前文件夹列表 + 资源 workspace），树从列表头唤起；空态必须 actionable；compact 隐藏 rail 并保证可读。

符合

L1 · 统一框架：rail + list + content + 48px head，全部模块一致

生产版所有模块共享同一壳层（PrimaryLayout + ResizablePanelGroup），head 高 48px（h-12），选中态浅紫、border-led 分离。布局纪律本身是好的——问题在模块怎么使用这个壳。

相反

L2 · Files：常驻树占据 list pane，"当前文件夹浏览"被挤到 workspace

契约 · Files has exactly two persistent panes: a current-folder browser/list and a resource workspace. Folder tree is an invoked popover or drawer from the browser head.

生产版左栏是常驻文件夹树（agents / profile / README）。点文件夹 → 右侧 workspace 变成文件夹列表；点文件 → 同一 workspace 变成文件详情。于是："浏览文件夹"和"查看资源"共用一块区域，树永远占据左栏——与契约的"左=当前文件夹浏览、右=资源 workspace、树按需唤起"恰好相反。契约还明确警告："Do not compose a Shell list pane around another list/detail split."

生产版 · 树常驻左栏（19-web-files.png）

左栏=树；右侧空态"选择一个文件查看详情"——不是 folder overview，也不是 actionable 空态（契约：不得是 unexplained blank pane）。

生产版 · 进入文件夹后（33-web-files-profile.png）

文件夹列表出现在右侧 workspace；头部只有标题"profile"，无路径、无返回按钮（契约：visible back action + current path）。"修改/大小"列全是 "—"。

偏差

L3 · 文件详情是"占位 + 跳转按钮"，不是 preview-first

契约 · readonly resources stay preview/detail-first；folder details with local selection and lightweight preview
生产版 · 选中 README（31-web-files-readme.png）

内容区只有元信息 + 紫色大按钮"打开文件详情"，正文是一句"完整内容将在弹出的文件详情中读取"。预览不是预览。

设计意图 · prototype 文件 sheet（42-proto-md-file.png）

设计意图：内容渲染 + Properties（reviewStatus/tags chips）+ Meta 尾栏（path/kind/format/size/modified）——正是契约说的 "focused sheet with `.meta` in the bottom tail"。

偏差

L4 · 联系人详情：技术标识外露 + 布局残留 bug

生产版 · 联系人详情（34-web-contact-detail.png）

①"聊天模型"显示完整 URL http://localhost:3000/settings/providers/undefineds.ttl#linx–lite——应显示模型名（copy 契约：advanced terms 留在设置）；②左栏右缘残留一个"AI"字符（渲染 bug）；③语音/视频死按钮占据 C 位。

设计意图 · prototype 联系人（02-module-联系人.png）

设计意图有信息分层：关系边界（Contact/Person/Agent）+ 共享上下文（Chat/Workspace/Artifacts）——生产版退化为一张大表单。

破损

L5 · Compact（480px）：rail 未隐藏、列表消失且无返回路径、内容溢出

契约 · Narrow layouts collapse supporting panes；Files compact: hide the global rail, one head, keep the active resource readable
生产版 · 480px 联系人详情（36-web-compact.png）

① rail 仍占 64px（契约要求 compact 隐藏）；② list pane 消失后没有任何返回列表的入口（头部只有"联系人"三个字）；③"聊天模型" URL 横向溢出屏幕；④语音/视频按钮被挤出可视区。mobile 非首要目标，但契约明确 tablet/narrow 要可用于 review——当前窄屏是死路。

Layer 4 · Modules

§4 模块层：生产 vs 设计意图的形态差距

prototype 代表经过设计思考的目标形态。逐模块对照，差距本身就是 backlog。

Layer 5 · Visual Tone

§5 设计气质：底盘是对的，破坏点集中在"外露"

符合

生产版视觉纪律整体达标

中性灰底 + 白色面板、1px border 承载结构、紫色仅用于当前模块/选中行/主按钮、系统字体、无渐变无 glow 无彩色阴影——与 DESIGN.md "restrained chrome, neutral surfaces, sparse accent, border-led separation" 一致。气质问题不在视觉系统，在内容外露：

断裂点违反的气质契约
语音/视频死按钮占据联系人详情 C 位"Prefer fewer visible modules over half-finished capability"——半成品不外露
聊天模型显示原始 URL、ID 显示 __secretary__、文件详情显示 URI 行"Keep advanced terms in settings/diagnostics"——技术标识不该出现在主路径
登录跳转 xpod 营销页（"Simplify Life with Your AI Secretary"）Avoid: "broad purple SaaS styling"、"emotion-led accent"——第三方页面也是产品体验
首屏空白（无状态说明）"Prefer transparent waiting/error state over a visually cleaner but silent experience"
"AI"残留字符、表格列文字重叠（prototype）完成度即气质：渲染 bug 比配色问题更伤"precise, trustworthy"

Conclusion

§6 结论与修复顺序（自顶向下）

一句话结论：框架（IA）已经收敛到正确形态；坍塌发生在"产品叙事落地"——chat 主舞台空白、信任信号缺席、Files 从资源浏览器退化为树+跳转按钮。设计意图（DESIGN.md / prototype）是清楚的，不需要重新设计，需要按层级把生产实现拉回契约。

① 产品层
先救首屏：Secretary welcome 真实渲染 + 主路径信任信号

welcome 不被自动选 thread 绕过（空 thread 也先显示 welcome + 可用 composer）；无 runtime/AI key 时显示明确状态与"前往设置"动作（宁要透明的等待，不要安静的空白）；头部或 rail 增加"当前空间"徽标（本机/云端 + 同步状态），从设置页"运行环境"上浮。

② 框架层
统一 Secretary 叙事 + 工作现场可见性

列表/头部/面包屑/联系人统一为同一名字与身份（"主理人 · 默认助手"，模型名不进面包屑）；工作现场（Thread/Workspace）以框架级槽位呈现，而不是 chat 私有侧栏。

③ 布局层
Files 结构拉回契约 + compact 修复

list pane 改为"当前文件夹浏览"，树改为从列表头唤起的 popover/drawer；头部加面包屑+返回；workspace 空态改为 folder overview / actionable 引导；文件 preview-first（内容渲染 + meta tail），"打开文件详情"降级为编辑入口；compact 隐藏 rail、提供返回、修复溢出。

④ 模块层
联系人/收藏补齐信息分层，下线半成品

联系人详情：URL→模型名、引入"关系边界/共享上下文"分层、语音/视频按钮下线或置灰标注；收藏空态加引导（"在聊天/文件中点星标，在这里回到它们"）。

⑤ 细节层
150+ 交互细节项

见 frontend-interaction-review.html（含 P0：审批失败草稿丢失 / AI 状态伪装消息 / 本机静默回退云端 / toast 系统调试值）。建议与 ①-④ 按模块合并排期，避免同一文件两次开工。

保持

做对了、应该保持的方向

  • IA 收敛：从 prototype 的 9 个 rail 入口收敛到 4 + 设置菜单 + 铃铛——"fewer visible modules" 的正确实践
  • 设置模块：完整度最高，"运行环境"徽标是信任信号的正确雏形
  • Inbox 弹层：异常中心的正确形态
  • 统一壳层：rail + list + content + 48px head 的框架纪律
  • 视觉底盘：macOS-native 克制气质达标，无 SaaS 化装饰
