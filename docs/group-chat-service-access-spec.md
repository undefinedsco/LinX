# 群聊服务授权与 Matrix 接口鉴权规格

状态：已定方向（2026-11-17，产品负责人确认“体验优先”），待 xpod 实现后由 LinX 切换。
范围：LinX 群聊（xpod Matrix 兼容层）的服务授权、调用鉴权、授权展示与收回。
不在本文范围：一对一聊天、AI 服务授权（`/api/applets/service-access/ai-connections`）现有行为不变。

## 1. 背景与问题

现状（LinX `staging` `f7f11bd`）：

- 读群消息：参与者用自己的 WebID 登录（DPoP）直接读群主 Pod 的房间（`shared-room-runtime.ts`）。邀请时群主已授予参与者 WebID 对房间容器的 Read/Append/Write（`matrix-room-access.ts`）。PR #70 起读取不再依赖额外凭据。
- 发消息、建群、邀请、接受邀请：浏览器为用户签发一把账号级客户端凭据（`sk-`，名为“LinX Matrix 群聊”），只存内存（`lib/matrix/pod-interface-access.ts`），调用用户“自己的” Matrix 服务，由它代表用户写入群主 Pod。

问题：

1. 刷新即丢凭据，刷新后第一次发消息要再授权。
2. 每次重新授权都留下一把未吊销的账号级凭据（依代码推断，未在服务端核实）。
3. 凭据权限是“以该用户身份打开其 Pod”，远大于一个群所需。
4. 与 AI 服务已采用的“授权给服务 WebID”模式不一致。

## 2. 决定

**照搬 AI 服务的授权模式，并用登录身份调用房间所在服务器：**

1. 房间所在的 xpod 有一个 Matrix 群聊服务身份（服务 WebID），服务端自持凭据。
2. 建群时，群主把**房间容器**的 Read/Append/Write 授予该服务 WebID，授权写在群主 Pod 的 ACP/WAC 中，长期有效、可收回。
3. 所有调用者（群主与参与者）用各自的 Solid 登录（DPoP）调用**房间所在服务器**的 Matrix 接口；服务器验证身份、检查该 WebID 的房间授权与 Matrix 成员关系，再以服务身份写入。
4. 浏览器与服务端都不再持有任何用户级 `sk-` 凭据。

保留的服务端行为：群助手接话（`reconcileEvent`）、`txnId` 去重、@ 权限检查（`authorizeTargets`）、事件号与资源 id 推导。

## 3. 授权体验（产品决定：体验优先）

- **随操作授权，不单独弹窗**：“创建群组”对话框显示一行说明“群消息会由 LinX 群聊服务写入这个群的文件夹”；点击“创建群组”即视为同意，期间不再出现任何授权步骤。
- **可见**：群“聊天信息”与 文件 › 该群文件夹 › 访问权限 中显示这条服务授权（服务名、范围、权限）。
- **可收回**：收回后该群不能收发消息，会话内明确提示原因与恢复方式，不静默失效。
- **参与者**：接受邀请只是一次点击，不改动参与者自己 Pod 的任何权限，不出现授权步骤。
- **以下情况必须单独显式确认**（对话框说明对象、范围与后果，用户可拒绝）：
  - 服务不属于托管该 Pod 的平台，例如第三方服务或群建在其他服务器上；
  - 授权范围超出该群文件夹；
  - 本机空间或独立空间中，服务身份与 Pod 所在地不一致。

`docs/approval-grant-design.md` 在本检出中缺失。本节是产品负责人对“群聊服务授权”这一类授权的明确决定，补齐统一授权设计时应吸收本节。

## 4. xpod 需求

### 4.1 服务身份与授权描述

- 提供 Matrix 群聊服务 WebID，凭据仅服务端保管，不下发到任何客户端。
- 提供授权描述接口，形状对齐 AI 服务，例如 `GET /api/applets/service-access/matrix-rooms?room=<roomContainer>` → `{ appletId, service: { webId }, resources: [{ id, url, access: { read, append, write }, members }] }`。`resources` 只能是该房间容器，不得扩大到 Pod 其他路径。
- 请求者是 Pod 主人且服务就是 Pod 主人自己的运行身份时，可与 AI 服务一样直接返回“无需授权”。

### 4.2 接受 Solid 登录调用

- Matrix 客户端接口接受标准 Solid-OIDC 访问令牌 + DPoP 证明。复用 Pod 资源服务器已有的校验实现，不另写。
- 校验必须包括：
  - 签名用签发方 JWKS 验证；
  - 签发方必须是该 WebID 资料声明的 `solid:oidcIssuer`；
  - `exp`、`iat` 和受众（audience）；
  - DPoP：`htm`、`htu` 与本次请求一致，`iat` 在时间窗内，`jti` 防重放缓存，证明公钥与令牌 `cnf.jkt` 一致。
- 跨服务器调用必须可用，例如参与者 Pod 在别处、群在本服务器。
- 保留对旧 `sk-` 凭据的兼容期，直到 LinX 切换完成；兼容期结束后移除。

### 4.3 授权判断与写入

- 每次读写同时检查两道：调用者 WebID 在该房间容器上的 ACP/WAC 授权，以及 Matrix 成员关系（未退出、未被封禁）。任一拒绝即拒绝。
- 写入的消息 `maker` 必须取自已验证令牌中的 WebID，绝不接受客户端传入的作者。
- 服务身份只写该房间容器，且只写本次操作对应的资源。
- 退出群或被移出时，同步撤销该成员的房间授权。
- 群助手触发规则不变：只能 @ 本房间已授权的助手（`authorizeTargets`）。

### 4.4 防护

- 对 Matrix 接口按 WebID 和来源做频率限制，并限制消息大小。
- 日志不得记录 `Authorization`、`DPoP` 头与令牌内容。
- 跨域策略只放行 LinX 前端域名；DPoP 头不会被浏览器自动附带，无 CSRF 风险。

## 5. LinX 改动（xpod 上线后）

1. 建群：在创建房间前后，按授权描述把房间容器授予群聊服务 WebID，复用 `grantAiServiceResourceAccess` 的 ACP/WAC 写入逻辑（不覆盖既有策略）。创建对话框加说明文案。
2. 调用：Matrix 客户端改用 `session.fetch`（DPoP），目标为房间所在服务器（由邀请中的存储地址解析），不再附带 `sk-`。
3. 删除：内存凭据（`pod-interface-access.ts` 的签发、导入、缓存、吊销）、原生账号页授权面板、“授权并继续”横幅及相关错误类型。保留真实权限失败（403）的提示。
4. 展示与收回：在群“聊天信息”和文件夹“访问权限”中显示服务授权，并支持收回；收回后会话给出明确提示。
5. 迁移：已存在的群如果没有服务授权，第一次由群主打开时自动补授权（属于“随操作授权”），参与者侧不受影响。

## 6. 验收用例

RC 双人群聊验收（`tests/e2e/specs/rc-shared-group.spec.ts`）全程不得出现任何授权步骤：建群 → 邀请 → 接受 → 双方收发 → 双方刷新后仍可读写。

服务端与单元测试至少覆盖：

| # | 用例 | 期望 |
|---|---|---|
| 1 | 用 Bob 的令牌发消息，但在请求体中伪造 `maker` 为 Alice | 写入的作者为 Bob，或请求被拒绝 |
| 2 | Bob 被移出群后发消息 | 403 |
| 3 | 重放一份旧的 DPoP 证明 | 401 |
| 4 | DPoP 证明的 `htu` 与请求地址不符 | 401 |
| 5 | 令牌签发方不是该 WebID 声明的签发方 | 401 |
| 6 | 收回群主对服务的房间授权后发消息 | 失败，界面提示原因 |
| 7 | 授权描述返回的资源超出房间容器 | LinX 拒绝写入授权并报错 |
| 8 | 刷新页面后读与发 | 均无需任何授权步骤 |
| 9 | 群助手被 @ | 仍能接话 |
| 10 | 同一 `txnId` 重试 | 不产生重复消息 |

## 7. 上线顺序

1. xpod 实现第 4 节，保留 `sk-` 兼容。
2. LinX 在 RC 上切换到第 5 节，双人群聊验收按第 6 节通过后发布。
3. 观察一个发布周期后，xpod 移除 `sk-` 兼容路径；运维侧清理历史遗留的“LinX Matrix 群聊”客户端凭据。
