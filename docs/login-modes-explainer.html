LinX 登录模式 Cloud / Local / Standalone

这里的登录不是填 AI provider key，而是让 LinX 拿到一个可以访问 Pod 的身份和会话。三种模式的核心差异只有两个问题：谁签发身份，数据放在哪个 xpod / SP。

IDP 管身份 SP / xpod 管数据 LinX 管入口、进程和路由 Local 默认可用 Cloud 分配 canonical SP URL

先看三层分工

登录页面要避免把“账号”“Pod 存储”“网络可达性”揉成一个按钮。正确叙事是三层： IDP 是身份权威，SP 是数据权威，LinX 是本机入口和路由协调者。

IDP：Identity Provider

负责账号、登录、OIDC consent、token、WebID 语义。Cloud 和 Local 模式通常使用 Cloud IDP；Standalone 使用本地 xpod 的 IDP。

SP：Storage Provider / xpod

负责 Pod 存储、资源读写、Pod URL、数据目录和服务可达性。Cloud 的 SP 在云端，Local / Standalone 的 SP 在本机 xpod。

LinX：Launcher + Router

负责选择登录路径、启动或复用本地 xpod、打开浏览器授权、保存本地会话， 并在多个等价入口中选择最优访问路径。

这三层分别回答什么

身份层
我是谁？谁给我签 token？ 由 IDP 回答。Cloud 身份和 Standalone 本地身份不是同一个 WebID。
存储层
我的 Pod 数据在哪里？通过哪个 base URL 写入？ 由 SP / xpod 回答。切换 Cloud SP 和 Local SP 不是普通路由优化。
入口层
当前设备走 localhost、LAN、公网直连还是隧道？ 由 LinX 基于 SP 暴露的候选入口和探测结果选择，但不能发明新的身份语义。

一致的用户心智

  • 都是先选空间，再走浏览器登录 / consent，再回到 LinX。
  • LinX 保存的是访问 Pod 的登录态，不把 AI provider key 当登录。
  • 登录成功后，业务数据都通过当前 SP 的 Pod URL 读写。
  • Local 的多个网络入口只是同一个 Local SP 的访问路径，不是多个 Pod。
  • 如果 WebID 的 storage 指向另一个 SP，MVP 应阻断而不是静默迁移。

三种登录模式

三个按钮的差别不应该靠长说明堆出来。每个模式都可以用“IDP 在哪里、SP 在哪里、 LinX 是否需要启动 xpod”讲清楚。

Cloud

账号和数据都托管在 Cloud，是最省心的默认路径。

IDP Cloud IDP
SP Cloud SP
  • LinX 不启动本地 xpod。
  • 用户不需要数据目录、公网域名、隧道或端口配置。
  • 登录、consent、Pod provisioning 都发生在 Cloud 路径。
  • 适合新用户、跨设备访问、希望最少网络配置的场景。

Local

身份接入 LinX / Cloud，数据落在本机 xpod。

IDP Cloud IDP
SP Local xpod
  • LinX 负责启动或复用本机 xpod。
  • 默认可由 Cloud 分配 node-*.undefineds.co 作为 canonical SP URL。
  • 用户自有 HTTPS origin 是高级路径，不是普通用户必须填写的入口。
  • localhost、LAN、隧道只是同一个 Local SP 的访问渠道。

Standalone

身份和数据都在本机，默认不依赖 Cloud。

IDP Local xpod IDP
SP Local xpod
  • LinX 启动本地 xpod，并打开本地账号页。
  • 默认只承诺本机可用，局域网和公网由用户网络决定。
  • 本地 WebID 和 Cloud WebID 分离，不能当作同一个身份偷偷合并。
  • 适合离线、本地试用、私有环境或不想接入 Cloud 身份的场景。

当前登录页先让用户选择 Cloud、Local 或 Standalone。这里不让用户手填 node-*.undefineds.co，也不把自有公网域名塞进默认登录路径； 域名只在 Local / Standalone 的高级服务配置里出现。

IDP 和 SP 的登录流程

用户看到的是“浏览器登录”，但背后其实有两条线：IDP 负责签发身份和授权， SP 负责提供 Pod 存储。LinX 把这两条线接回当前应用。

1

LinX 选择模式

用户选择 Cloud、Local 或 Standalone。Local / Standalone 会先准备本地 xpod 进程和 base URL。

2

浏览器去 IDP

Cloud / Local 去 Cloud IDP；Standalone 去本地 xpod 的账号页和 OIDC 入口。

3

IDP 登录授权

用户完成账号登录、Pod 选择或 consent。IDP 签发 token，并保持 WebID 语义稳定。

4

回调到 LinX

LinX 通过本机 callback 或等价桥接完成 token exchange，并保存可恢复的本地会话。

5

通过 SP 读写 Pod

后续业务数据写入当前 SP。Cloud 写 Cloud SP，Local / Standalone 写本机 xpod。

同一套流程在三种模式下怎么落点

Cloud
浏览器访问 Cloud IDP
SP 是 Cloud SP
LinX 只保存 Cloud 会话，不管理本地 xpod
Local
浏览器访问 Cloud IDP
SP 是本机 xpod
默认使用 Cloud 分配的 Local SP canonical URL；用户自有 URL 是高级路径
Standalone
浏览器访问本地 xpod IDP
SP 是同一个本地 xpod
不依赖 Cloud 身份，本地 WebID 独立存在

选择 SP 空间后，后台实际做什么

用户点的是一个空间入口，但 LinX 后台会把“身份 issuer”和“数据 storage provider” 固定成一组登录尝试，避免登录成功后写错 Pod。

1. 记录目标空间

Cloud 记录 Cloud SP；Local / Standalone 记录本地 xpod 空间类型和本机服务状态。

2. 准备本地 SP

Local / Standalone 会启动或复用 xpod，并等待端口、数据目录和健康检查 ready。

3. 取得 canonical URL

Local 从 Cloud provisioning 取得 publicUrl 和 provisionCode； Standalone 使用本地 xpod URL。

4. 发起 OIDC 登录

Local 用 Cloud issuer 加 provisionCode 打开授权；Standalone 打开本地 issuer。

5. 绑定 WebID storage

Local 登录完成时 Cloud 和目标 SP 确认 Pod，Cloud WebID 的 profile/card#me 会写入 solid:oidcIssuer 和 solid:storage，其中 solid:storage 指向选中的 Local SP。

6. 回调并保存会话

LinX 通过本机 callback 完成 token exchange，保存 issuer、storageProviderUrl 和可恢复的 Solid 会话。

7. 校验写入目标

如果 WebID profile 的 solid:storage 不等于当前选中的 SP，阻断进入， 不静默改写到 Cloud。

8. 后续读写走该 SP

业务数据、Solid DB base 和首个写入都使用 selected SP Pod URL 前缀。

注册时怎么区分 storage

LinX 不让用户在登录框里手填 storage。系统先选定空间，再用 spaceKind、provisionCode、publicUrl 和 canonical SP URL 推导目标 storage。Cloud / Local 走选中的 SP canonical URL 加 WebID slug；Standalone 走本机 xpod URL；Custom 则必须先读 profile 里的 solid:storage，再校验它仍落在当前 provider 下。

Inrupt SDK 负责什么

SDK 只负责 OIDC 登录，不负责决定 storage。它主要吃 oidcIssuer、redirectUrl、clientName、 tokenType，登录完成后 LinX 再从 session.info.webId 和 WebID profile 读取结果。

Inrupt SDK 入参按模式怎么填

SDK 的 login() 入参不包含 storage provider。LinX 自己保存 storageProviderUrl 作为当前登录尝试的上下文；Cloud 侧注册 / 绑定则通过 provisionCode 找到目标 SP。

Cloud oidcIssuer 填 Cloud issuer，redirectUrl 填 LinX callback； 无 provisionCode，登录后 storage 应该落在 Cloud SP。
Local oidcIssuer 仍填 Cloud issuer；授权 URL 追加 provisionCode。 LinX pending state 记录 Local canonical storageProviderUrl，用于回调后校验。
Standalone oidcIssuer 填本地 xpod issuer，redirectUrl 仍回 LinX； 没有 Cloud provision，WebID 和 storage 都由本地 xpod 提供。

profile/card RDF 示例

下面是 Local 模式下最关键的 profile/card 片段：WebID 在 Cloud， solid:storage 指向选中的 Local SP Pod。这里写的是 canonical storage， 不是 localhost、LAN 或隧道访问地址。 

@prefix foaf: <http://xmlns.com/foaf/0.1/> .
@prefix solid: <http://www.w3.org/ns/solid/terms#> .

<https://id.undefineds.co/alice/profile/card#me>
  a foaf:Person ;
  foaf:name "Alice" ;
  solid:oidcIssuer <https://id.undefineds.co/> ;
  solid:storage <https://node-0000.undefineds.co/alice/> .

解释时抓住两点：solid:oidcIssuer 回到身份签发方； solid:storage 回到数据所在的 SP。LinX 登录成功后要读取并校验这两个事实， 再决定业务数据写到哪里。

LinX 怎么管理 xpod 进程

LinX 不应该重新定义 IDP 或 SP 的语义。它的职责更像本机 launcher 和 process manager：该启动时启动，该复用时复用，该检查时检查。

Cloud 没有本地 xpod 进程。LinX 只打开 Cloud 登录并保存会话。
Local 需要本地 xpod 作为 SP。LinX 准备配置、端口、数据目录和可达入口。
Standalone 本地 xpod 同时是 IDP 和 SP。LinX 打开本地账号与授权流程。
→

LinX Process Manager

启动 / 复用 检查本地 xpod 是否已运行；没有则按当前模式启动。
配置边界 写入端口、base URL、canonical public URL、数据目录和模式配置。
健康检查 等待 xpod ready，再打开账号页或继续登录回调。
隧道协作 把 selected canonical URL 接到本机 xpod；隧道只改变访问渠道。
会话保存 保存 LinX / Solid 登录态，后续尽量 refresh 和复用。
访问路由 在同一 SP 的等价入口中探测、排序并选择最快可用路径。

Local 路径会先等 xpod ready

用户选择 Local 后，LinX 先启动或复用本机 xpod，再继续 Cloud 登录。 localhost 是本机访问渠道；登录完成后业务数据写入 Local SP， canonical URL 由 Cloud provisioning 或用户自有 HTTPS origin 决定。

Local / Standalone 的网络可达性

Local 和 Standalone 的复杂度不在登录按钮，而在“同一个本地 xpod 可以通过哪些地址到达”。 LinX 可以优化访问路径，但只能在同一 SP、同一数据目录、同一身份语义成立时优化。

1

localhost

当前设备访问本机 xpod 的最优路径。最快、最少网络依赖，适合 CLI、TUI、桌面端。

2

LAN

同一局域网设备访问本机 xpod。需要监听地址、防火墙和局域网路由允许访问。

3

公网直连

高级 Local 路径下，用户自己的 HTTPS 域名直接打到本机或反代。

4

隧道

本机不可公网直连时使用。隧道把 selected canonical URL 接到本机 xpod， 不改变身份或 storage URL。

5

Cloud SP

只属于 Cloud 模式。它不是 Local SP 的自动 fallback，除非明确做迁移或同步方案。

最优路径选择规则

当前设备能走 localhost 就优先走本机；同网设备优先 LAN； 远程设备走公网直连或隧道。这个排序只在多个 URL 被证明属于同一个 xpod / SP 时成立。

不能做的事

不能因为 Local 入口不可达就静默切到 Cloud SP；不能把 localhost、LAN、 隧道临时入口写成 solid:storage；也不能把 Standalone 的本地 WebID 偷偷当成 Cloud WebID。

外网域名在哪里录入

默认登录 overlay 不直接录入外网域名。Local 的默认路径是 Cloud provisioning 分配 Cloud-managed canonical URL；只有用户要使用自有 HTTPS origin 时，才在服务配置里填写 pod.example.com 这类域名。

Local 首次配置 设置页的“公网入口”区块提供“自有公网域名（可选）”输入框；留空就使用 Cloud 分配的 canonical URL。
Service 管理 服务管理弹窗里有“公网域名（可选）”，用于修改 Local 服务的 user-managed canonical domain。
Standalone Standalone 也有“公网域名（可选）”，但它不接 Cloud 身份；留空时只承诺本机或局域网可用。

对外讲解时的顺序

不要从“我们支持多少 URL”开始讲。先讲三层模型，再讲三个模式，最后再讲 Local 的网络路径，这样用户不会把公网、隧道、LAN 误解成新的登录身份。

顺序 要讲清楚的事 一句话
1 IDP / SP / LinX 三层 IDP 管身份，SP 管数据，LinX 管入口和进程。
2 Cloud / Local / Standalone 三个模式的差别，是身份权威和数据权威放在哪里。
3 LinX 管理 xpod Cloud 不启动本地 xpod；Local 和 Standalone 由 LinX 启动、检查和复用。
4 Local / Standalone 网络可达性 localhost、LAN、公网直连、隧道只是同一个本地 SP 的不同访问路径。

一句话总结

Cloud 是云端身份加云端数据；Local 是 Cloud 身份加本机数据； Standalone 是本机身份加本机数据。LinX 只负责把正确的 IDP、SP、xpod 进程和访问路径接起来。
