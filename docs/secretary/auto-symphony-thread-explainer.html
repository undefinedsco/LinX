先讲 Reconciler，再讲 Automode，最后讲 Symphony

这套 spec 的故事线是：所有协作先进入 Thread；Reconciler 观察 Thread 里的每条消息和事件，并决定下一步投递给谁；Automode 和 Symphony 都只是不同规模下的投递策略。

Thread-first AI Secretary Automode Symphony
1. Reconciler

每条进入 Thread 的消息、事件、审批、交付都先被 Reconciler 观察，再按当前模式投递给合适的人或 AI。

2. Automode

在最简单的三人群聊里，只改变“用户和 worker 聊”还是“Secretary 和 worker 聊”。

3. Symphony

把一个 Thread 扩展成多组 Threads：main thread 管用户和 Secretary，worker threads 管 Secretary 和 workers。

1. Reconciler：所有来源都能往 Thread 投消息

Reconciler 不代替 Secretary 做语义判断。它的角色是观察 Thread：谁往里面投了消息，是什么事件，当前 Thread policy 是什么，然后决定下一步要唤醒谁。

User 人类直接把消息投进 Thread。
AI Chat Reply Secretary 或 assistant 响应他人后，把回复投进 Thread。
Worker Reply worker 执行、询问、汇报后，把结果投进 Thread。
Task / Schedule 时间触发，或者时间触发后产生 task event。
Runtime / Delivery 审批、输入、工具请求、阶段交付和证据都能进入 Thread。

关键点：来源很多，但都先写入 Thread；Reconciler 只做路由和唤醒，不替代 Secretary 做复杂语义判断。

最简单的模型：三人群聊

  • 一个 Thread 里有 User、Secretary、Worker 三个参与者。
  • User 可以直接发消息进 Thread。
  • Secretary 和 Worker 都是 AI participant，响应别人之后再把消息投进 Thread。
  • 不同模式不需要换产品形态，只需要改 Reconciler 的投递行为。

Thread policy 改变的是投递

  • direct：用户消息投给默认 assistant 或 worker。
  • auto：审批、输入、阻塞先投给 Secretary。
  • symphony：Issue、Task、Delivery、Run 事件投给 Secretary 或 assigned worker。
  • review：Delivery 边界投给 Secretary 或 reviewer。

多人多 AI 群聊：Thread 是共享房间，不是点对点链路

三人群聊只是最小模型。真实产品里，一个 Thread 可以同时有多个人、多个 AI、多个 worker 或 reviewer。所有参与者都往同一个 Thread 里写消息；Reconciler 根据 mention、订阅、角色、风险和当前 policy 决定谁需要被唤醒。

User A 直接发问题、目标、确认和反馈。
User B 可以补充上下文、提出约束或做验收。
Secretary 负责解释意图、协调权限、归纳状态。
One Chat / One Thread 所有人和 AI 看到的是同一个可审计时间线。Reconciler 不让 agent 彼此私下直接叫醒，而是统一从 Thread 事件做投递。
Research AI 被 mention、订阅或任务策略唤醒后回复。
Worker AI 负责执行具体任务、提交进度和 Delivery。
Reviewer AI 在 review policy 或 Delivery 边界上被唤醒。
Mention @research 或明确点名时，Reconciler 唤醒对应 AI。
Subscription 订阅这个 Thread 的 AI 可以被特定事件或关键词唤醒。
Role policy approval 给 Secretary，delivery 给 reviewer，task dispatch 给 worker。
Noise control 不是每条消息都唤醒所有 AI；Reconciler 要去重、限流和选择目标。

Automode 不需要先想成“高级自动化”。它就是同一个三人群聊里的投递策略：off 的时候主要是 User 和 Worker 聊；on 的时候主要是 Secretary 和 Worker 聊。产品侧仍然可以看成一个单聊。

Automode 下的 Approval 和 Grant

Approval 是一次 runtime 请求，Grant 是可复用的授权事实。Automode 打开后，这些请求不是直接打断用户，而是先被 Reconciler 投给 Secretary；Secretary 根据已有 grant、风险和上下文决定是否处理，处理不了再问用户。

1. Worker 请求 runtime 发出 command / file / permission / input approval。
2. 进入 Thread 请求成为 Thread 里的 control event 或 Inbox item。
3. Reconciler 投递 auto policy 把请求投给同 Thread Secretary。
4. Secretary 查 Grant 已有授权就按范围处理；没有或风险过高就问用户。
5. 回写结果 approval 决策、grant 变化、证据和审计写回控制记录。

3. Symphony：从一个三人 Thread 变成多组 Threads

Symphony 不是 Automode 的升级版，而是切换“用户当前在跟谁聊”。/symphony off 时，用户直接跟当前 worker/backend peer 聊；/symphony on 时，用户跟 Secretary 控制面聊，Secretary 再把工作拆到多组 worker threads。worker threads 是 Secretary 和 Worker 聊，approval 和 grant 由同 Thread 的 Secretary 优先处理。

Main Thread

User ↔ Secretary 识别目标、查重、确认范围、接收汇总和最终请示。
也可以开 Automode 如果 main thread 也 auto on，Secretary 可以继续推进当前主线并在阻塞时问人。
→

Worker Threads

Thread A：Secretary ↔ Worker A 自动托管执行；approval / grant 先由这个 Thread 的 Secretary 处理。
Thread B：Secretary ↔ Worker B 独立任务、独立证据、独立 Delivery，必要时回 main thread 协调。
Thread C：Secretary ↔ Worker C 可以共享 workspace，也可以按 Thread 分配不同 worktree。

/symphony off：用户直接跟 Worker / Backend Peer 聊

  • 用户输入直接进入当前 worker/backend peer 的普通 chat。
  • 可以回答问题、继续对话、处理当前 backend 会话上下文。
  • 不会默认把一句话升级成 Issue，也不会默认拆 Task 或派 worker。
  • 如果要委派，需要切到 /symphony on 或由已有产品路径触发。

/symphony on：Secretary 带控制面 skills

  • 先判断这句话是普通聊天、新 Issue、已有 Issue 更新、steering，还是需要追问。
  • 先查 open Issues，能归并就归并，避免重复创建工作。
  • 把目标拆成 worker 可执行的 Task，并选择目标 worker Thread。
  • 跟踪 Delivery、Evidence、Run 状态，把阻塞和变更带回 main thread。

Secretary skills：判断、编排、收口

  • 读 main thread 用户意图，决定是否进入 Symphony 工作流。
  • 维护 Issue 的范围、状态、优先级、拆分和验收边界。
  • 给 worker 投递任务 brief，并处理 approval / grant 的升级路径。
  • 验收 Delivery 和 Evidence，决定完成、重开、变更或继续派工。

Worker skills：执行、验证、报告

  • 读取被分配的 Task / brief，不重新定义 Issue 范围。
  • 在自己的 worker thread 和 workspace 内完成实现、调试或研究。
  • 需要权限、输入或范围变更时，先报告给对端 Secretary。
  • 用 Delivery / Evidence 汇报结果、测试、风险和变更请求。

Issue 是穿针引线的主线对象

Symphony 不是把多个聊天窗口简单堆起来。Issue 是把 main thread 的用户意图、多个 worker threads 的执行、Delivery 的交付和 Evidence 的证明串成一条线的控制记录。

Main Thread User 和 Secretary 确认目标、范围、歧义和最终接受。
Issue 记录当前工作主线：要解决什么、属于哪个范围、现在状态如何。
Tasks Issue 被拆成 worker 可执行的任务，每个任务有明确验收边界。
Worker Threads Secretary 和 worker 在独立 Thread 中执行，默认 automode。
Delivery / Evidence worker 提交阶段结果、证据、测试、风险和变更请求。
Back To Issue Secretary 根据交付更新 Issue：完成、阻塞、继续、重开或改范围。

Symphony 负责什么

  • 判断用户输入是普通聊天、新 Issue、已有 Issue 更新、steering，还是需要追问。
  • 把复杂工作拆成 Task，并选择目标 worker Thread。
  • 用 Delivery / Evidence / Run 状态收口 worker 输出。
  • 把无法自动处理的审批、授权、范围变化带回 main thread。

每个 worker Thread 的默认行为

  • 默认是 automode：Secretary 与 Worker 对话，用户不直接参与。
  • Worker 需要 approval 或 input 时，先问同 Thread Secretary。
  • Secretary 能按 grant 和策略处理就处理，不能处理就升级给 main thread 或用户。
  • Worker 的结果通过 Delivery 和 Evidence 回到控制面，而不是靠零散聊天记忆。

最后要记住的关系

Thread 是消息现场，Reconciler 是投递器，Automode 和 Symphony 只是不同规模下的投递策略。

Automode 三人 Thread 中，决定 User 跟 Worker 聊，还是 Secretary 跟 Worker 聊。
Symphony 多组 Threads 中，让 Secretary 带控制面 skills 去拆分、派工和收口。
Issue 把 main thread、worker threads、Delivery 和 Evidence 串成一条主线。
