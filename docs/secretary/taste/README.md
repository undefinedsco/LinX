# Secretary Taste 能力域

Status: active
Last reviewed: 2026-06-07
Conversation with: 主理人 LinX

主理人的 taste 能力——帮用户建立和精炼一套共享词汇表，让每次判断都有据可依。

---

## 核心理念

### Taste = 用户的词汇表

Taste 不是偏好强度（「更简洁一点」），而是词汇精确性——**什么算什么、什么不算，边界在哪。**

```
偏好：简洁 ←→ 详细               （连续刻度）
词汇：吞异常 ←→ 转换 ←→ 兜底     （离散边界）

用户说"别吞异常"不是在表达偏好强度。
是在定义一个词——什么是吞异常、什么不是。
主理人和执行者之间的 gap，
不是"我希望更简洁"，
是"你这个 catch 块，在我的词汇表里叫吞异常——这是不对的。"
```

**主理人是用户词汇表的共同作者。** 每次纠正是一个新词或一次边界精炼。用户的 AGENTS.md 是词汇表初稿，每次纠正让词汇表更精确。

## 数据模型：卡片·目录·链接

这三个原子能力是词汇表的最小完备集。一项不可拆、一项不可少。

### 卡片——词汇条

一个不可再分的 taste 信号。一次纠正。一句话。一个词的边界定义。

```
卡片 = 词 + 定义 + 边界 + 正例 + 反例

例：
  词：吞异常
  定义：捕获异常后既未处理也未向上传递，导致上层无法感知错误
  正例：空 catch 块、catch 后只打 log 不抛
  反例：catch 后转换并抛出（这是转换，不是吞）、
        最外层统一兜底（这是兜底，不是吞）
```

卡片小到不能再拆——拆了就没意义。大到自成一句——不需要上下文也能读懂。不预分类、不替用户抽象。

### 目录——词汇索引

不是分类。分类是替用户做决定。目录是让用户看见自己建了多少词、每个词在哪些项目里、哪些词很久没用过。

目录是一组 SPARQL 查询，不是静态页面。

### 链接——词间关系

两张卡片之间的关系。链接的类型**从用户行为里自然长出来**，不预定义。

```
第一次用"吞异常"和"错误处理"之间的链接 → 无标签
第三次同样的模式出现 → 主理人问：
  "这个关系是不是该有个名字？叫'属于'还是别的？"
```

不预设关系类型。用户说叫「矛盾」就叫矛盾，说不用就不用。

## 数据模型：标注系统

卡片定义了词的意思。标注让词落到实体上。

没有标注，词汇表就是字典——翻完合上，不知道用在哪儿。
没有词汇表，标注就是乱贴标签——今天叫 A 明天叫 B。

### 标签自生长

标签体系不设计——主理人自己长。

```
第一条纠正："别吞异常"

主理人做的事：
  1. 建词汇卡片：吞异常（定义+边界+正反例）
  2. 给触发这条纠正的 message 打标：taste:swallowing-exceptions
  3. 第一条标注就是这个标签的诞生
```

### 标签生命周期的自我管理

| 能力 | AI 做什么 | 用户做什么 |
|---|---|---|
| 创建标签 | 纠正时自动建 | 不需要知道 |
| 合并标签 | 发现两个标签连续共现 10 次 → 提议合并 | 确认 or 拒绝 |
| 拆分标签 | 发现标签下出现明显不同的子模式 → 提议拆分 | 确认 or 说"先别拆" |
| 废弃标签 | N 天未用标记 inactive | 不需要管 |
| 建立层级 | 从共现模式推导上下位关系 | 不需要管 |
| 映射用户说法 | 用户说"炫技"→ 查找最近似已有标签 | 确认 or 说"这是新词" |

标签可以多层，但层级从使用中长出来——主理人发现某个标签下出现了明显不同的子模式，自己拆。

```
taste:error-handling
  ├── taste:swallowing-exceptions
  ├── taste:over-catching
  └── taste:bare-exception

taste:code-complexity
  ├── taste:over-engineering
  │   ├── taste:unnecessary-factory
  │   └── taste:over-abstraction
  └── taste:over-simplification
```

### 标注和卡片·目录·链接的关系

```
卡片（词汇条）：
  吞异常 = 定义 + 边界 + 正反例
  → 回答：这个词是什么意思

标注（标签系统）：
  给 message 打 taste:swallowing-exceptions
  → 回答：这条 message 是在说这个词

目录：
  查所有标注了 taste:swallowing-exceptions 的 message
  → 回答：这个词被用过多少次、在什么场景下

链接：
  taste:swallowing-exceptions → 和 taste:error-handling 的关系
  → 回答：这个词属于哪一类
```

卡片定义语义，标注落到实体，目录和链接让词被检索和关联。用户只需要做一件事：**该说不对的时候说不对，该说对的时候说对。** 标签体系的维护全是主理人的后台任务。

## 三层架构

```
Layer 1 — 用户界面：AGENTS.md
  用户写的自然语言大原则
  词汇表初稿
  "简洁优先"、"别吞异常"

Layer 2 — 操作流程：System Prompt
  主理人怎么读 AGENTS.md、怎么判断、怎么记
  怎么写卡片、怎么链接、怎么自查
  和用户共同演化——用户纠正主理人的工作方式，prompt 就更新

Layer 3 — 本体定义：@undefineds.co/models（语义网 RDF）
  Card、Link、Project 的 class 和 predicate 定义
  每个 predicate 的 domain/range/语义
  机器可校验、跨会话一致
  用户不可见——用户不需要知道 RDF
```

| 层 | 谁写 | 用什么 | 解决什么问题 |
|---|---|---|---|
| 用户界面 | 用户 | AGENTS.md | 用户表达自己 |
| 操作流程 | 用户+主理人共演 | System Prompt | 主理人怎么工作 |
| 本体定义 | 模型团队 | RDF/OWL | 词本身是什么意思、边界在哪 |

## 产品整合：LLM Wiki 落地

LLM Wiki 的三个操作分别以不同方式整合到产品中：

### Query → 工具（开放查询层）

任何 agent、任何场景都能调词汇表，不绑定主理人。

```
执行者生成代码前：  "这个项目对错误处理有什么要求？" → Query tool
主理人审批时：      "这段产出有没有踩到已知词汇？" → Query tool
用户查看：          "我关于'简洁'都说过什么？" → Query tool
```

返回的不是全文搜索结果——是匹配的词条定义、边界、正反例、最近相关纠正。

### Ingest → 事件驱动 + 周期式

```
事件驱动：
  用户纠正 → 即时写卡片

周期式（会话结束、每天、每周）：
  主理人回溯审批记录
  → 用户 approve 但没纠正的产出里，有没有隐含新词汇？
  → 连续多次纠正同一个方向 → 合并成一条精炼词条
  → 用户放过的和之前 reject 的之间，边界在哪？

用户不纠正也是一种信号。主理人该自己去发现。
```

### Lint → 启发式任务

不跑定时脚本。条件触发：

```
触发条件                       检查什么
──────────────────────      ──────────────────
同义词条超过 2 条             是不是该合并？
一个词条 30 天没被触发         标记待确认
两个词条边界出现重叠           问用户：一个词还是两个？
一个词在不同项目里用法不同     标记项目特化
新纠正和已有词条矛盾           标记冲突，问用户取舍
```

## 反馈链路

反馈链路是所有能力的前提。链路不通，任何记忆都是死的。

```
用户说"不对，应该……"
  → 主理人判断：新词还是边界精炼？
  → 写一张卡片
  → 下次类似场景，检索 → 应用
  → 用户确认 / 再次纠正 → 更新卡片

链路通了之后：
  → 周期式 ingest 自己发现新模式
  → 启发式 lint 自己保持词汇表健康
  → Query tool 让任何 agent 都能用
```

## 设计原则

### 1. 不看 benchmark 看产品

产品化水平由用户行为定义。分两层：

**过程指标**（监控标注和串珠是否正常运转）：

| 指标 | 定义 |
|---|---|
| 标注准确率 | 消息标注后，用户在下游通过行为间接修正标注的比例 |
| 信号压缩比 | Thread 消息数 / 总消息数——标注层是否有效过滤了噪音 |
| Thread 断裂率 | 一颗珠子找不到前因的比例——标注层是否漏了关键信号 |

**核心指标**（衡量用户是否觉得对味）：

| 指标 | 定义 |
|---|---|
| 采纳率 | 主理人建议的 revise/reject，用户点了「接受」的比例 |
| 纠正衰减 | 同类场景第 1 次纠正 vs 第 N 次纠正的频率曲线 |
| 误报率 | 主理人说「不对」但用户说「过」 |
| 漏报率 | 用户手动纠正但主理人没提前标出来 |
| 冷启速度 | 从 AGENTS.md 到第一个有效判断所需的纠正次数 |
| 归因准确率 | 主理人判断「这次纠正是因为历史哪条对话」，用户确认的比例 |
| 归因深度 | 同一张卡片的版本迭代次数。深度 1 = 一次纠正就稳了。深度 3 = 经历了三次精炼。不需要推断因果链——看版本 diff 即可 |

> 归因深度是独有的产品级指标——它衡量的是同一 taste 词条的迭代历史，而非跨会话因果推断。用户不需要确认归因——版本记录自己会说话。

> 实验室分数是参考。用户行为是答案。

- **原子性**：边界和可组合性。一次纠正一张卡片，不搅在一起。
- **灵活性**：用户可个性化。系统不替用户分类、不替用户抽象。用户的表达第一位。

只原子不灵活 → 碎片。只灵活不原子 → 泥球。

### 3. 冷启动从用户开始，过程用户可打开

用户写 AGENTS.md → 主理人第一次判断 → 纠正 → 卡片。

用户随时看到：主理人提取了什么、哪些在强化、哪些在衰减、哪些是推测的。

**用户不是训练数据，是 taste 的唯一来源。**

### 4. 词汇表从用户行为长出来，边界用语义网锁定

LLM 发现新词、精炼边界。语义网（RDF class/predicate）定义词的类型和边界——任何代码读到它都知道这个词到底是什么意思。

**LLM 是词汇表的作者，语义网是词汇表的出版社。**

## 训练管道：从反馈链路到在线 RL

反馈链路的每一环都在产训练数据，终极目标是在线 RL——用户纠正即时反馈回模型。

### 管道的四层

```
Layer 1 — 信号积累（实时）
  每次用户纠正/确认 → 标注层自动打标 → 存入信号池
  不需要用户额外操作。对话即标注。

Layer 2 — 偏好对构造（准实时）
  信号池攒够后：
    ┌─ 否定 + 新词汇 → rejected（被拒的产出）
    ├─ 肯定 → chosen（被接受的产出）
    └─ 否定 + 归因成功 → rejected + 因果链（不只是拒了什么，还有为什么拒）
  → 产出 (prompt, chosen, rejected) 三元组
  → 按项目分组——不同项目 taste 不同，不混着训
  → 归因信息注入 rejected 侧：让模型知道不是因为结果不好，是中间某一步违反了词汇定义

Layer 3 — 训练（周期性）

  冷启动（信号不足 50 对/项目）：
    不训模型，训 prompt
    → 偏好对转成卡片（词汇表精炼）
    → 卡片注入 system prompt / AGENTS.md
    → 主理人 in-context 学习
    → 冷启动的指标是纠正衰减，不是模型 loss

  积累期（50-200 偏好对/项目）：
    → DPO（Direct Preference Optimization）
    → 不需要单独训 reward model
    → LoRA adapter 按项目加载
    → 切项目 = 切 adapter，不切 prompt

  成熟期（200+ 偏好对/项目）：
    → P-RLHF：每个用户独立 user model，不和大众偏好混
    → 在线 RL（自托管模型 + proxy gateway）
    → 用户纠正即时反馈回模型

Layer 4 — 评估（持续）
  过程指标：纠正衰减下降？归因准确率提升？冷启速度变快？
  核心指标：采纳率提升？误报/漏报率下降？
  训练本身的健康度：偏好对质量分布、DPO loss 轨迹、adapter 切换后指标变化
```

### 关键设计决策

1. **冷启动不训模型，训 prompt。** 前 50 次纠正不够 RL——强行训只会过拟合。偏好对转词汇卡片，用 in-context 学习过渡。

2. **Taste 按项目隔离训练。** 不同项目 taste 可能相反。训练数据不跨项目混。LoRA adapter 按项目加载。

3. **偏好对比「对/错」更丰富。** 归因层提供 cause annotation。DPO 不只看 chosen vs rejected，还看 rejected 为什么被拒——违反了什么词汇定义。

4. **在线 RL 的工程门槛取决于部署方式。**
   - API 模型（Step 3.7 Flash、DeepSeek）→ 在线 RL 不现实，周期性 DPO 微调
   - 本地模型（Ollama）→ AReaL/OpenClaw-RL proxy gateway 直接接

5. **单步因果为训练，多步因果为壁垒。** 业界在线 RL（OpenClaw-RL、PAHF、RetroAgent）都把因果归因做到单步——找到「用户这句话在纠正上一步」就够了。没有人在跨会话串联因果链。
   - 单步因果 → 训练信号的来源（可直接复用 OpenClaw-RL 的 directive signal 提取）
   - 多步因果 → 产品壁垒（标注层 + Thread + 归因）。没人做 = 护城河
   - **归因深度**是新指标——衡量系统是否真的在积累长期记忆，而非每次从零判断

### 归因简化：放弃长链条因果推断，用版本记录替代

经过对业界实践的深入调研（OpenClaw-RL、PAHF 止步单步因果；GraphGPO、T-STAR 困于单任务轨迹），结论是：**不需要跨会话因果链归因。**

核心假设：

```
会话内：消息 = 信息载体
会话外：文档（AGENTS.md、卡片）= 信息载体

用户批评时，系统只做一次自检：
  检索相关文档 → 有吗？
  ├── 没有 → 归因：文档缺失 → 记卡片 v1
  ├── 有但搜不到 → 归因：检索不到 → 优化检索
  └── 有且搜到了 → 语义网推理也跑了
      → 但推理结论和用户判断不一致
      → 归因：推理不准确
      → class/predicate 定义不够精确 → 精炼语义网
```

对第三种归因——语义网的 class 边界问题：

```
卡片在、语义网在、推理也跑了。
但 class 的 indicator 只定义了「空 catch 块」和「只打 log」。
代码是 catch (e) { throw new BusinessException(e) }——没有吞异常？

用户说：不对，你转换了异常类型但丢了原始堆栈——这就是吞。
推理对了 indicator，错了边界。

归因不是检索不到——是 class 定义不够精确。
每次纠正不只在改卡片文本，也在更新 class 定义和推理约束。
```

三个归因：

```
1. 文档缺失 → 记卡片 v1
2. 检索不到 → 优化检索
3. 推理不准确 → 精炼 class/predicate 定义
```

为什么这是聪明而非 tradeoff：

1. **版本 diff 天然就是因果解释。** 卡片从 v1 → v4，每一次为什么改、改了什么，都在 diff 里。不需要推断「msg-201 和 msg-12 的因果关系」——版本记录已回答。

2. **用户的记忆也是版本化的。** 你记得的是「吞异常」的定义经历了三次修正——不是记得「6 月 3 日 msg-47 和 6 月 10 日 msg-132 有因果链」。系统的记忆模型应该和用户的记忆模型一致。

3. **长链条归因在错误的数据模型上做推断。** 对话不是状态存储单元——对话是编辑行为。把编辑行为串成因果链，是在错误的数据模型上做推断。版本记录直接在正确的数据模型（文档 = 实体）上做记录。

4. **系统能自检的，不需要推断；版本能追溯的，不需要归因。** 每次纠正 → 搜文档 → 有就精炼，没有就创建。Thread 不是因果推断链——是版本演化轨迹。

> 长链条归因是被 memory benchmark 和 failure attribution benchmark 的语境带偏了。LinX 从一开始就在建实体模型（卡片·目录·链接），版本记录是实体模型的自然延伸。放弃长链条归因不是承认做不到——是发现这件事本来就不该做。

### 归因深度的最终定义

```
归因深度 = 同一张卡片经历的版本迭代次数

深度 1：纠正 → 文档缺失 → 建卡片 v1
深度 3：同一类纠正三次 → v1 → v2 → v3
  → 意味着前两次精炼不够
  → 不需要推断因果链——只需要看版本 diff

版本记录就是 Thread。
diff 就是因果解释。
归因不需要用户确认——系统自查。
```

### 两类任务 → 三类任务

反馈链路产出三类任务，对应训练数据：

```
任务 1 — 答问题（事后判断）
  主理人读文档，判断产出对不对味。
  文档是 prompt 的一部分，判断是 completion。训判断能力。

  DPO 构造：
    prompt = 语义网 + 上下文 + 文档
    rejected = 错误判断（"过"但用户说不对 / "不对因为X"但用户说不是因为X）
    chosen  = 正确判断（用户纠正后的判断）

任务 2 — 改文档（文档精炼）
  文档被用户纠正，从 vN 升级到 v{N+1}。
  文档是 completion，其余是 prompt。训编辑能力。

  分两种子场景：

  即时改文档：
    prompt = 用户第 N 次纠正时的全部上下文  
    rejected = 没改 or 改错了
    chosen  = v{N+1}（用户纠正后该写的新版本）
    训反应速度——"用户纠正了，我该更新"

  hindsight 改文档（核心创新）：
    prompt = 用户第 N 次纠正时的全部上下文（那时只有 v{N-1}）
    rejected = vN（当时模型写的——不够好，触发第 N+1 次纠正）
    chosen  = v{N+2}（第 N+1 次纠正后才确定的最终版）
    训前瞻深度——"用户只纠正了这一次，我该直接写出最终版"

任务 3 — 审指令（事前对齐）
  主理人在执行者动笔前，补上执行者看不到的上下文。
  用户原话是 prompt，补全后的指令是 completion。训判断力。

  DPO 构造：
    prompt   = 用户原始指令 + 项目文档
    rejected = 原样转发（没补上下文）
    chosen   = 补充后的指令

  审指令不插话——改的是发给执行者的那份 user input。
  用户只发一条消息，执行者拿到补全版，一次做对。
```

### 三种产品模式

```
Autopilot 模式：
  用户说意图 → 主理人全权处理 → 执行者执行
  用户不碰中间环节。

Copilot 模式：
  用户说意图 → 主理人改 user input → 执行者执行
  用户发一条消息，主理人在中间补上下文。
  用户感知不到主理人在干什么——只知道执行者第一次就做对了。
  审指令的主要落地方式。

Review 模式（事后）：
  用户说意图 → 执行者执行 → 产出 → 主理人标问题
  答问题的主要落地方式。
```

Copilot 模式的判断边界：

```
能直接改的（不打断用户）：
  - 盲点明确，补充信息确定
  - 项目文档有的规则（"别放顶级"）
  - AGENTS.md 有的偏好（"用函数式"）
  - skills 有的用法（"xpod 写 Pod，不写本地文件"）

需要问用户的（打断一次）：
  - 两个方向都合理
  - 边界模糊
  - 新场景，没文档

不改的（纯粹执行）：
  - 用户指令已包含全部上下文
  - 没有隐含决策需要揭示
```

### 实操发现：xpod-cli skill 的读者错位

当前 xpod-cli skill 的 description 只覆盖 CLI 开发者场景，没覆盖主理人 AI 的使用场景——
导致主理人不知道「什么时候该用 xpod 写 Pod 而不是 write 本地文件」。

这是审指令要解决的一类问题：不是用户的指令有盲点——是已有 tool/skill 的文档没覆盖所有目标读者。主理人应在看到 tool 调用和文档 gap 时标出。

修复方向：skill description 需要同时标注 CLI 开发者和主理人 AI 两种目标读者。

### 实操案例：审指令的两个入参

以下两个真实案例说明了主理人在 copilot 模式下审指令的价值——
不是事后 review，是事前补盲点。

**案例 1：linx status-line 放错了层级**

```
场景：用户让 agent 做 status-line 功能。agent 做完汇报：

  显式交付：linx status-line 命令，功能跑通 ✅
  隐含决策：放在顶级命令层，和 login / chat / install 同级

问题：
  agent 只汇报了第一件。
  项目的目录结构卡片说：工具类配置放 config 下。
  但 agent 没查——它不知道这个规则的存在。

如果主理人在 copilot 模式：
  审指令 → 查项目卡片 → "工具冲突放 config 下"
  → 改 user input：补上 "放在 linx config 下，别放顶级"
  → agent 拿到补全的指令，一次做对
```

**案例 2：主理人自己没识别 xpod-cli skill 的读者错位**

```
场景：主理人在本场对话中记录设计结论，全用了 write 写到本地文件。
xpod 在路径上，Pod 已认证，xpod put/rdf/obj 都能用。

为什么没用：
  xpod-cli skill 的 description = "designing, implementing, reviewing, testing"
  → 主理人判断：我是主理人 AI，不是 CLI 开发者 → skill 不触发
  → xpod 能力在，但没被当成"写 Pod 的工具"来用

问题：
  不是用户指令有盲点——是已有 skill 的文档没覆盖所有目标读者。

如果主理人在审指令：
  看到用户说 "记录到文档" → 查 tool/skill → 发现 xpod 可用但 skill 只写 CLI 场景
  → 应该标出：xpod-cli skill 存在但 description 没覆盖主理人 use case
  → 在改文档里补一条："主理人用 xpod 写 Pod，不写本地文件"
```

两个案例的共同结构：

```
执行者/主理人产出了东西 → 放错了/用错了工具
  → 不是能力不够——是不知道上下文
  → 上下文在项目文档里，在 skill 的另一个读者视角里
  → 主理人的工作：在执行前查上下文，补进指令
  → 审指令 ≠ review —— 审指令发生在执行者动笔前
```

### 三层 DPO 训练信号，来自同一条反馈链路

hindsight 的本质：

```
时间线：
  t1: 用户第一次纠正 → 模型写 v1
  t2: 用户第二次纠正 → 模型写 v2（不够好，触发了 t3）
  t3: 用户第三次纠正 → 模型写 v3（终于对了）

取 t2 作为 prompt（不是 t3）：
  如果取 t3——用户已经说得很清楚了，任何模型都能写出 v3，训练没学到任何东西。
  取 t2——那时只有 v1，用户说了和第二次同样的话。
  模型应该跳过 v2，直接写出 v3。

这是 hindsight（事后聪明）训练——用最终对的结果，教模型在中间那步就该这样做了。
不是 RL——不需要奖励模型、不需要 rollout。
数据和算法解耦——DPO 可以，SFT 也可以。
```

> hindsight（小写）是机器学习通用概念（最早来自 Hindsight Experience Replay）。
> 不是 Vectorize.io 的 Hindsight 产品（四网络记忆系统，LongMemEval 91.4%）。

### 三层 DPO 训练信号，来自同一条反馈链路

```
用户第三次纠正"这是第三次了"
  ↓
标注：否定 + 引用历史
  ↓
├── 答问题 DPO：prompt=上下文+文档, chosen=正确判断, rejected=错误判断
├── 即时改文档 DPO：prompt=第三次纠正时的上下文, chosen=v3, rejected=没改
└── hindsight 改文档 DPO：prompt=第二次纠正时的上下文, chosen=v3, rejected=v2

三股训练信号，来自同一条纠正。
答问题 → 训判断力。即时改文档 → 训反应速度。hindsight → 训前瞻深度。
```

## 关键设计结论

1. **Taste 不是技术能力，是用户表达。** 顾问不需要比执行者更懂技术，只需要更懂用户。

2. **Taste 不是贴在人身上的标签，是沉积在项目里的判断层。** 同一个人在不同项目里的 taste 可能完全相反。

3. **Taste 的本质是词汇精确性，不是偏好强度。** 不聊「更简洁一些」，聊「这个在我的词汇表里叫过度设计」。

4. **现有 benchmark 只能参考，不能衡量产品化水平。** 得分再高的记忆系统也只是管线，不等于用户觉得对味。

5. **不让 LLM 自由发挥记忆——给方法论脚手架。** Zettelkasten（原子卡片 + 不预设分类）最适合冷启动。

6. **LLM Wiki 落地不是做一个新产品。** Query 是工具，Ingest 是事件+周期，Lint 是启发式。三件事三种整合方式，没有一件需要用户学新命令。

7. **AGENTS.md 写原则，System Prompt 写方法，语义网定义边界。** 各管一层，不混。

8. **主理人输出只有三种：✅ 过 / 🔄 不对 / ❓ 不确定。** 不确定比瞎判重要——每次不确定就是喂词汇表的机会。

9. **标注不只是一层标签——它是 thread 的过滤器。** 90% 的日常对话不包含 taste 信号，标注层自动过滤。只有「否定+新词汇」「肯定+引用历史」「元对话」这类信号消息入 thread。标注精度越高，thread 越干净。

10. **现有 memory benchmark 的真实性有限——它们测的是「在干草堆里找针」，LinX 的场景是「在真实对话里串因果珠链」。** 针是故意插进去的，haystack 是填充文本。LinX 的 haystack 是真实对话，主理人不能直接忽略；珠子不是预设的——需要自己判断什么是珠子。没有一个 benchmark 测这个。

11. **归因没有 ground truth——它只存在于用户确认的那一刻。** 现有归因研究全集中在「系统哪里出错了」，没有人在研究「用户这次纠正是因为上次哪次对话」。归因准确率是产品指标，不是 benchmark 分数——用户确认才算对。Multi-Perspective Failure Attribution 的观点很关键：同一个纠正可能有多个合理归因，归因不是找唯一根因，是列出可信假设，用户确认。

12. **反馈链路的每一环都是训练数据。** 每次纠正 = 一组偏好对。每次肯定 = 一组确认信号。不需要额外标注——对话本身就是训练。

13. **冷启动训 prompt，不训模型。** 前 50 次纠正不够 RL。偏好对 → 词汇卡片 → system prompt。用户感知到主理人在进步，背后只是 prompt 在变。纠正衰减持续下降才切换到 DPO。

14. **在线 RL 的终极目标可行，但需要基础设施。** 自托管模型 + AReaL/OpenClaw-RL proxy gateway → 用户纠正即时反馈。API 模型只能走周期性 DPO。两条路线取决于部署方式，但信号积累层是共用的。

15. **放弃长链条因果归因——用版本记录替代。** 每次用户批评只做一件事：搜文档。没有就建 v1，有就精炼到 v{N+1}。版本 diff 就是因果解释，不需要推断。Thread 不是因果推断链——是版本演化轨迹。这不是承认做不到跨会话因果推断——是发现这件事本来就不该做：用户的记忆是版本化的语义，系统的记忆也应该是。

16. **归因不是两个选项，是三个：文档缺失、检索不到、推理不准确。** 第三种对应语义网 class 边界问题——卡片在、语义网在、推理也跑了，但 class 定义的 indicator 不够精确，导致推理结论和用户判断不一致。每次纠正不只在改卡片文本，也在更新 class 定义和推理约束。

17. **反馈链路产出两类任务：答问题（训判断力）和改文档（训编辑力）。** 答问题——文档是 prompt，判断是 completion。改文档——文档是 completion，其余是 prompt。"谁被修改，其余全是 prompt"。

18. **Prompt 取第二次纠正，不是第三次。** hindsight 训练——用事后才知道的最终版 v3 回填到第二次纠正的决策点，让模型学会在有限信息下直接写出最终版。取第三次当 prompt 意味着用户已经说得很清楚了，任何模型都能写对——训练没学到任何东西。

19. **不需要陷入 RL——hindsight 训练是因果训练，不是强化学习。** 不需要奖励模型、不需要 rollout、不需要在线更新。数据构造逻辑独立于算法选择——DPO 可以，SFT 也可以。

20. **三层训练信号来自同一条反馈链路。** 每次纠正同时产出：答问题 DPO（训判断）、即时改文档 DPO（训反应）、hindsight 改文档 DPO（训前瞻）。三股信号，同一条纠正。

21. **审指令是第三类任务——在事前，不是事后。** 主理人不插在执行者和用户之间，插在用户和执行者之间。不是在产出后纠偏，是在执行前审题。改的是发给执行者的 user input，不是打断用户对话。

22. **Copilot 模式——主理人不插话、改输入。** 三种产品形态：Autopilot（全权处理）、Copilot（改 user input）、Review（事后标问题）。Copilot 是审指令的落地方式。盲点明确直接改，不确定就问用户，没盲点就不动。

23. **Skill description 需要覆盖所有目标读者。** xpod-cli skill 只写了 CLI 开发者场景，没写主理人 AI 场景——导致主理人不知道什么时候该用 xpod 写 Pod。这是审指令要标出的一类问题：不是用户指令有盲点，是已有文档没覆盖所有读者。

24. **主理人的产出应进 Pod，不是本地文件。** xpod 在路径上、Pod 已认证、RDF/obj/put 都能写——记录 agent 和主理人应该走 xpod，不是 write 到本地 markdown。
