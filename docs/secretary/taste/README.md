# Secretary Taste 能力域

Status: active product boundary; research notes retained
Last reviewed: 2026-09-28
Conversation with: 主理人 LinX

主理人的 taste 能力——在共同做事中帮助用户表达、保存和修订有来源、有适用条件的判断；词汇表是其中一种表达，不替代用户具体目标。

本轮按 [产品体验 R6](../../../../homepage/docs/specs/personal-ai-product-experience-r6.md) RD04–08、F01–04 与 [LW-04/07/11](../../../../homepage/docs/reviews/product-r6-2026-09-28/linx-workflows.md) 修订。入口是“工作”的反馈、“知识”的来源与修订、“我的 AI”的方法和个人模型；不新增 taste 数据库或训练权威。

**现行产品边界**：纠正先用于本次工作；用户可选择仅此次、保留知识草稿、确认有范围的长期知识。候选发现仅在已选择的记录/整理范围内进行。沉默、收藏、执行批准不构成正例、知识确认或训练授权。模型训练另核对用途和材料，实际算法/数量门槛/评估/发布由 Foundry 合同决定。后文研究段落是候选方法和历史观察，不是已验证能力或自动执行规则。

## 核心理念

### Taste 的表达：判断、条件与用户词汇

Taste 包含目标之间的取舍、偏好和适用条件；词汇精确性帮助表达**什么算什么、什么不算，边界在哪**。用户可以用自然语言表达，无需先定义术语或写 AGENTS.md。

```
偏好：简洁 ←→ 详细               （连续刻度）
词汇：吞异常 ←→ 转换 ←→ 兜底     （离散边界）

用户说"别吞异常"不是在表达偏好强度。
是在定义一个词——什么是吞异常、什么不是。
主理人和执行者之间的 gap，
不是"我希望更简洁"，
是"你这个 catch 块，在我的词汇表里叫吞异常——这是不对的。"
```

**主理人协助用户提炼判断。** 一次纠正可能只对当前任务适用，也可能形成待确认的新词或条件修订。已有 AGENTS.md 可以作为用户方法的来源之一，但不是冷启动必填表单。

## 数据模型：卡片·目录·链接

这三个原子能力是词汇表的最小完备集。一项不可拆、一项不可少。

### 卡片——词汇条

一条有来源、范围和状态的判断或词汇定义；并非每次纠正都必须新建卡片。

```
卡片 = 判断/词义 + 来源 + 适用条件/例外 + 状态/版本；正反例在有依据时补充

例：
  词：吞异常
  定义：捕获异常后既未处理也未向上传递，导致上层无法感知错误
  正例：空 catch 块、catch 后只打 log 不抛
  反例：catch 后转换并抛出（这是转换，不是吞）、
        最外层统一兜底（这是兜底，不是吞）
```

卡片应可读且能回到来源，不用失去情境的一句话代替完整判断。系统提炼与用户原话分开；不预分类、不替用户确认抽象。

### 目录——词汇索引

不是分类。分类是替用户做决定。目录是让用户看见自己建了多少词、每个词在哪些项目里、哪些词很久没用过。

目录是一组 SPARQL 查询，不是静态页面。

### 链接——词间关系

两张卡片之间的关系。链接的类型**从用户行为里自然长出来**，不预定义。

```
第一次用"吞异常"和"错误处理"之间的链接 → 无标签
第三次同样的模式出现 → 主理人问：
  "这个关系是不是该有个名字？叫'属于'还是别的？"
```

用户可以用自己的标签表达关系；显示名称不自动成为正式 class/predicate。既有语义优先复用，新关系的持久定义经共享模型与 proposal 治理。

## 数据模型：标注系统

卡片定义了词的意思。标注让词落到实体上。

没有标注，词汇表就是字典——翻完合上，不知道用在哪儿。
没有词汇表，标注就是乱贴标签——今天叫 A 明天叫 B。

### 标签自生长

候选标签可在用户已授权的记录/整理范围内发现；它们不自动成为正式词汇、本体或长期规则。

```
第一条纠正："别吞异常"

主理人做的事：
  1. 先修正当前任务
  2. 按用户选择保留知识草稿，关联这条 message 与原话
  3. 提议词义、条件及已有对象匹配；用户确认后才进入相应长期知识范围
```

### 标签生命周期与确认

| 能力 | 系统可做什么 | 用户控制与边界 |
|---|---|---|
| 发现标签 | 在获准范围提出候选，查已有对象 | 可仅此次、保留草稿或确认；不自动创建正式本体 |
| 合并/拆分 | 展示依据、涉及来源及建议差异 | 用户确认范围；不同项目或同名对象不自动合并 |
| 未使用提示 | 标明最后使用与不确定性 | 不因时间过去自动废弃仍有效的判断 |
| 建立关系 | 提出有来源的关系与条件 | 语义变更走已有受控 proposal；不另立标签权威 |
| 映射用户说法 | 提供候选匹配及原定义 | 可接受、纠正或认为是新概念 |

标签只作为既有资源的投影/关联。系统可以减少重复整理，但不能用后台“自生长”替代用户对长期判断和用途的选择。

### 标注和卡片·目录·链接的关系

```
卡片（词汇条）：
  吞异常 = 定义 + 边界 + 正反例
  → 回答：这个词是什么意思

标注（标签系统）：
  给 message 打 taste:swallowing-exceptions
  → 回答：这条 message 是在说这个词

目录：
  查所有标注了 taste:swallowing-exceptions 的 message
  → 回答：这个词被用过多少次、在什么场景下

链接：
  taste:swallowing-exceptions → 和 taste:error-handling 的关系
  → 回答：这个词属于哪一类
```

卡片定义语义，标注落到实体，目录和链接让词被检索和关联。用户可以直接说对、不对或补充条件；系统先服务当前工作，再依已选范围提出可检查的整理。无需每次反馈都弹确认，长期确认与训练授权也不得省略。

## 三层架构

```
Layer 1 — 用户界面：工作中的方法/反馈与“我的 AI”
  用户的目标、标准、条件与范围
  AGENTS.md 等已有文件可作为来源，不是唯一编辑入口
  "简洁优先"、"别吞异常"

Layer 2 — 操作流程：System Prompt
  主理人怎么读 AGENTS.md、怎么判断、怎么记
  怎么写卡片、怎么链接、怎么自查
  方法修改按本次/默认范围及有效版本提交；一次纠正不直接改永久 prompt

Layer 3 — 本体定义：@undefineds.co/models（语义网 RDF）
  Card、Link、Project 的 class 和 predicate 定义
  每个 predicate 的 domain/range/语义
  机器可校验、跨会话一致
  普通操作不要求理解 RDF；相关语义和技术详情仍可按需查看
```

| 层 | 谁写 | 用什么 | 解决什么问题 |
|---|---|---|---|
| 用户界面 | 用户 | 自然语言反馈、方法编辑，关联既有文件 | 用户表达自己与适用范围 |
| 操作流程 | 用户+主理人共演 | System Prompt | 主理人怎么工作 |
| 本体定义 | 模型团队 | RDF/OWL | 词本身是什么意思、边界在哪 |

## 产品整合：LLM Wiki 落地

LLM Wiki 的三个操作分别以不同方式整合到产品中：

### Query → 工具（开放查询层）

任何具有相应资料与用途权限的 agent 都能查询词汇表，不绑定主理人；共享查询能力不意味着跨身份或跨项目无条件可读。

```
执行者生成代码前：  "这个项目对错误处理有什么要求？" → Query tool
主理人审批时：      "这段产出有没有踩到已知词汇？" → Query tool
用户查看：          "我关于'简洁'都说过什么？" → Query tool
```

返回的不是全文搜索结果——是匹配的词条定义、边界、正反例、最近相关纠正。

### Ingest → 获准范围内的候选整理

用户纠正首先作用于本次任务。选择保留后，系统可检查已有资源，形成新建、修订或关联的知识草稿；显示原话与提炼、来源、条件和例外。冲突不能静默覆盖，失败保留原版与草稿。

在用户已选择的会话/资料范围和整理频率内，可聚合重复候选并批量审阅。没有收到纠正只意味着没有明确反馈，不能当作赞同或训练正例；批准执行只证明允许动作，不能证明认可结果。

确认知识使其按选定范围可用；实际任务引用记录版本。训练用途、样本范围和快照另行授权，不能从知识确认继承。

### Lint → 启发式任务

不跑定时脚本。条件触发：

```
触发条件                       检查什么
──────────────────────      ──────────────────
同义词条超过 2 条             是不是该合并？
一个词条 30 天没被触发         标记待确认
两个词条边界出现重叠           问用户：一个词还是两个？
一个词在不同项目里用法不同     标记项目特化
新纠正和已有词条矛盾           标记冲突，问用户取舍
```

## 反馈链路

反馈链路是所有能力的前提。链路不通，任何记忆都是死的。

```
用户说"不对，应该……"
  → 修正当前工作
  → 用户选仅此次，或在已选范围保留知识草稿
  → 核对来源、提炼、条件、例外及现有冲突
  → 确认后按范围可用；新任务检查条件并引用具体版本
  → 用户可修订或撤回；训练授权仍独立

链路通了之后：
  → 获准范围内的周期整理提出新模式候选
  → 启发式 lint 提示冲突和待核对项，不自动确认
  → Query tool 让获准 agent 按适用范围使用
```

## 设计原则

### 1. 不看 benchmark 看产品

产品化水平由用户行为定义。分两层：

**过程指标**（监控标注和串珠是否正常运转）：

| 指标 | 定义 |
|---|---|
| 标注准确率 | 消息标注后，用户在下游通过行为间接修正标注的比例 |
| 信号压缩比 | Thread 消息数 / 总消息数——标注层是否有效过滤了噪音 |
| Thread 断裂率 | 一颗珠子找不到前因的比例——标注层是否漏了关键信号 |

**核心指标**（衡量用户是否觉得对味）：

| 指标 | 定义 |
|---|---|
| 采纳率 | 主理人建议的 revise/reject，用户点了「接受」的比例 |
| 纠正衰减 | 同类场景第 1 次纠正 vs 第 N 次纠正的频率曲线 |
| 误报率 | 主理人说「不对」但用户说「过」 |
| 漏报率 | 用户手动纠正但主理人没提前标出来 |
| 冷启速度 | 从 AGENTS.md 到第一个有效判断所需的纠正次数 |
| 归因准确率 | 主理人判断「这次纠正是因为历史哪条对话」，用户确认的比例 |
| 归因深度 | 同一张卡片的版本迭代次数。深度 1 = 一次纠正就稳了。深度 3 = 经历了三次精炼。不需要推断因果链——看版本 diff 即可 |

> 修订次数可用于观察同一判断的变化，不证明学习质量或因果。版本记录提供改动依据；系统推断与用户确认分开，这些观察指标不替代保留任务评估。

> 实验室分数是参考。用户行为是答案。

- **原子性**：边界和可组合性。一次纠正一张卡片，不搅在一起。
- **灵活性**：用户可个性化。系统不替用户分类、不替用户抽象。用户的表达第一位。

只原子不灵活 → 碎片。只灵活不原子 → 泥球。

### 3. 冷启动从用户开始，过程用户可打开

用户先做一项实际工作 → 看建议与依据 → 纠正 → 可选择留下草稿。已有 AGENTS.md/方法可作来源，不要求先写配置。

用户随时看到：主理人提取了什么、哪些在强化、哪些在衰减、哪些是推测的。

**用户不是训练数据，是 taste 的唯一来源。**

### 4. 词汇表从用户行为长出来，边界用语义网锁定

LLM 发现新词、精炼边界。语义网（RDF class/predicate）定义词的类型和边界——任何代码读到它都知道这个词到底是什么意思。

**LLM 是词汇表的作者，语义网是词汇表的出版社。**

## 个人模型产品合同与算法研究边界

知识记录、运行时使用和真实模型训练是三个层次。反馈可成为候选信号，不是每条反馈天然属于训练集；来源、用途、权限、质量和隔离评估均须满足。

### 现行工作链

1. 在用户已选记录范围内保存原记录和可选择的反馈；知识草稿/确认不等于训练授权。
2. 从“我的 AI”或同一知识对象进入材料核对：入选/排除、来源版本、用途、处理位置/外发对象、资源和费用条件，训练/调试/保留评估集分开。
3. 实际提交依 Foundry 协议返回任务；结果未知查原任务，取消请求不等于已停止。缺协议先保留准备草稿和准确状态，不模拟成功。
4. 训练完成须有真实可执行产物与谱系，候选不自动启用。用相同基础模型与相同获准知识/规则/工具条件的新保留任务比较，允许无改善。
5. 发布与按范围启用分别记录期望 release、可服务/加载版本和实际 Run 使用。回退影响后续任务，不改历史实际版本。
6. 撤回资料分别处置未来引用、后续训练和现存产物，不承诺旧权重立即遗忘。

### 非产品合同的研究候选

DPO、SFT、LoRA/适配器、蒸馏、在线 RL 与 hindsight 数据构造可以作为 Foundry 研究备选；本文件不预选算法、供应商或部署方式。不用固定50或200条反馈作为通用训练/升版门槛，也不把“改 prompt”命名为参数训练。项目、条件、来源和授权范围可用于材料分组，但是否共训由用户目的与领域评估决定。

后续论文/框架名称、历史成绩与案例保留为研究笔记，本轮未重新核实，不能转成产品能力承诺、训练门槛或评价结论。正式评估须由版本化产物与独立证据支持。

### 归因简化：放弃长链条因果推断，用版本记录替代

经过对业界实践的深入调研（OpenClaw-RL、PAHF 止步单步因果；GraphGPO、T-STAR 困于单任务轨迹），结论是：**不需要跨会话因果链归因。**

核心假设：

```
会话内：消息 = 信息载体
会话外：文档（AGENTS.md、卡片）= 信息载体

用户批评时，系统只做一次自检：
  检索相关文档 → 有吗？
  ├── 没有 → 归因：文档缺失 → 记卡片 v1
  ├── 有但搜不到 → 归因：检索不到 → 优化检索
  └── 有且搜到了 → 语义网推理也跑了
      → 但推理结论和用户判断不一致
      → 归因：推理不准确
      → class/predicate 定义不够精确 → 精炼语义网
```

对第三种归因——语义网的 class 边界问题：

```
卡片在、语义网在、推理也跑了。
但 class 的 indicator 只定义了「空 catch 块」和「只打 log」。
代码是 catch (e) { throw new BusinessException(e) }——没有吞异常？

用户说：不对，你转换了异常类型但丢了原始堆栈——这就是吞。
推理对了 indicator，错了边界。

归因不是检索不到——是 class 定义不够精确。
这种纠正可能提出卡片或语义定义的修订建议；不是每次都修改 class，正式变更须按来源、范围与既有治理确认。
```

三个归因：

```
1. 文档缺失 → 记卡片 v1
2. 检索不到 → 优化检索
3. 推理不准确 → 精炼 class/predicate 定义
```

为什么这是聪明而非 tradeoff：

1. **版本 diff 提供可审查的改动证据，不单独证明因果。** 卡片从 v1 → v4 可记录改动、作者与理由；用户动机和跨消息关系仍需要来源依据，不能从 diff 自动补出。

2. **用户的记忆也是版本化的。** 你记得的是「吞异常」的定义经历了三次修正——不是记得「6 月 3 日 msg-47 和 6 月 10 日 msg-132 有因果链」。系统的记忆模型应该和用户的记忆模型一致。

3. **长链条归因在错误的数据模型上做推断。** 对话不是状态存储单元——对话是编辑行为。把编辑行为串成因果链，是在错误的数据模型上做推断。版本记录直接在正确的数据模型（文档 = 实体）上做记录。

4. 系统可以检索已有文档并提出新建或修订候选；是否持久化按当前范围和用户选择。版本轨迹关联 Thread，但不把两者视为同一对象。

> 长链条归因是被 memory benchmark 和 failure attribution benchmark 的语境带偏了。LinX 从一开始就在建实体模型（卡片·目录·链接），版本记录是实体模型的自然延伸。放弃长链条归因不是承认做不到——是发现这件事本来就不该做。

### 归因深度的最终定义

```
归因深度 = 同一张卡片经历的版本迭代次数

深度 1：纠正 → 文档缺失 → 建卡片 v1
深度 3：同一类纠正三次 → v1 → v2 → v3
  → 意味着前两次精炼不够
  → 不需要推断因果链——只需要看版本 diff

版本记录关联 Thread，二者不是同一资源。
diff 是改动证据，不等于经验证的因果。
系统可提出归因候选；涉及用户理由或长期判断的结论仍按知识确认合同处理。
```

### 两类任务 → 三类任务

以下是已授权材料的研究性任务构造示例，不是默认采集或自动训练规则；chosen/rejected 必须有与评价目标相符的证据，沉默或执行批准不能充当标签：

```
任务 1 — 答问题（事后判断）
  主理人读文档，判断产出对不对味。
  文档是 prompt 的一部分，判断是 completion。训判断能力。

  DPO 构造：
    prompt = 语义网 + 上下文 + 文档
    rejected = 错误判断（"过"但用户说不对 / "不对因为X"但用户说不是因为X）
    chosen  = 正确判断（用户纠正后的判断）

任务 2 — 改文档（文档精炼）
  文档被用户纠正，从 vN 升级到 v{N+1}。
  文档是 completion，其余是 prompt。训编辑能力。

  分两种子场景：

  即时改文档：
    prompt = 用户第 N 次纠正时的全部上下文
    rejected = 没改 or 改错了
    chosen  = v{N+1}（用户纠正后该写的新版本）
    训反应速度——"用户纠正了，我该更新"

  hindsight 改文档（核心创新）：
    prompt = 用户第 N 次纠正时的全部上下文（那时只有 v{N-1}）
    rejected = vN（当时模型写的——不够好，触发第 N+1 次纠正）
    chosen  = v{N+2}（第 N+1 次纠正后才确定的最终版）
    训前瞻深度——"用户只纠正了这一次，我该直接写出最终版"

任务 3 — 审指令（事前对齐）
  主理人在执行者动笔前，补上执行者看不到的上下文。
  用户原话是 prompt，补全后的指令是 completion。训判断力。

  DPO 构造：
    prompt   = 用户原始指令 + 项目文档
    rejected = 原样转发（没补上下文）
    chosen   = 补充后的指令

  补充内容作为 Secretary 的执行输入投影，保留原话、实际 maker 与依据。
  可以不打断无歧义的当前工作，但用户能检查补了什么；不承诺一次做对。
```

### 三种协作情境（不是新增控制模式）

- 持续推进：Secretary 在已允许的范围继续工作，超出范围或遇到未知需要用户判断；不称全权处理。
- 执行前补上下文：保留用户原话，以 Secretary 身份补充有来源的方法/知识，展示可检查摘要；不能无痕改写成人类消息。材料、权限或目标有实质歧义时先解决该决定。
- 事后检查：对结果给出依据、条件与改进建议；用户可认可、否定或仅用于本次。

这些是使用情境，不新增 Autopilot/Copilot/Review 三档开关。auto、peer 选择、后端批准策略与长期 grant 按 [Auto contract](../auto-symphony-contract.md) 及 [Capability contract](../capability-contract.md) 分别处理。明确上下文可在既有权限内补充，不擅自扩大授权、训练用途或持久方法。

### 实操发现：xpod-cli skill 的读者错位

当前 xpod-cli skill 的 description 只覆盖 CLI 开发者场景，没覆盖主理人 AI 的使用场景——
导致主理人不知道「什么时候该用 xpod 写 Pod 而不是 write 本地文件」。

这是审指令要解决的一类问题：不是用户的指令有盲点——是已有 tool/skill 的文档没覆盖所有目标读者。主理人应在看到 tool 调用和文档 gap 时标出。

修复方向：skill description 需要同时标注 CLI 开发者和主理人 AI 两种目标读者。

### 实操案例：审指令的两个入参

以下两个真实案例说明了主理人在 copilot 模式下审指令的价值——
不是事后 review，是事前补盲点。

**案例 1：linx status-line 放错了层级**

```
场景：用户让 agent 做 status-line 功能。agent 做完汇报：

  显式交付：linx status-line 命令，功能跑通 ✅
  隐含决策：放在顶级命令层，和 login / chat / install 同级

问题：
  agent 只汇报了第一件。
  项目的目录结构卡片说：工具类配置放 config 下。
  但 agent 没查——它不知道这个规则的存在。

如果主理人在 copilot 模式：
  审指令 → 查项目卡片 → "工具冲突放 config 下"
  → 保留原话，Secretary 补充有来源的执行约束："放在 linx config 下，别放顶级"
  → agent 拿到补全的指令，一次做对
```

**案例 2：主理人自己没识别 xpod-cli skill 的读者错位**

```
场景：主理人在本场对话中记录设计结论，全用了 write 写到本地文件。
xpod 在路径上，Pod 已认证，xpod put/rdf/obj 都能用。

为什么没用：
  xpod-cli skill 的 description = "designing, implementing, reviewing, testing"
  → 主理人判断：我是主理人 AI，不是 CLI 开发者 → skill 不触发
  → xpod 能力在，但没被当成"写 Pod 的工具"来用

问题：
  不是用户指令有盲点——是已有 skill 的文档没覆盖所有目标读者。

如果主理人在审指令：
  看到用户说 "记录到文档" → 查 tool/skill → 发现 xpod 可用但 skill 只写 CLI 场景
  → 应该标出：xpod-cli skill 存在但 description 没覆盖主理人 use case
  → 在改文档里补一条："主理人用 xpod 写 Pod，不写本地文件"
```

两个案例的共同结构：

```
执行者/主理人产出了东西 → 放错了/用错了工具
  → 不是能力不够——是不知道上下文
  → 上下文在项目文档里，在 skill 的另一个读者视角里
  → 主理人的工作：在执行前查上下文，补进指令
  → 审指令 ≠ review —— 审指令发生在执行者动笔前
```

### 已授权反馈的 DPO/hindsight 研究构造

hindsight 的本质：

```
时间线：
  t1: 用户第一次纠正 → 模型写 v1
  t2: 用户第二次纠正 → 模型写 v2（不够好，触发了 t3）
  t3: 用户第三次纠正 → 模型写 v3（终于对了）

取 t2 作为 prompt（不是 t3）：
  如果取 t3——用户已经说得很清楚了，任何模型都能写出 v3，训练没学到任何东西。
  取 t2——那时只有 v1，用户说了和第二次同样的话。
  模型应该跳过 v2，直接写出 v3。

这是 hindsight（事后聪明）训练——用最终对的结果，教模型在中间那步就该这样做了。
不是 RL——不需要奖励模型、不需要 rollout。
数据和算法解耦——DPO 可以，SFT 也可以。
```

> hindsight（小写）是机器学习通用概念（最早来自 Hindsight Experience Replay）。
> 不是 Vectorize.io 的 Hindsight 产品（四网络记忆系统，LongMemEval 91.4%）。

### 已授权反馈的候选数据分支

```
用户第三次纠正"这是第三次了"
  ↓
标注：否定 + 引用历史
  ↓
├── 答问题 DPO：prompt=上下文+文档, chosen=正确判断, rejected=错误判断
├── 即时改文档 DPO：prompt=第三次纠正时的上下文, chosen=v3, rejected=没改
└── hindsight 改文档 DPO：prompt=第二次纠正时的上下文, chosen=v3, rejected=v2

同一条已授权且有评价依据的纠正，可能构造多个候选数据分支；不得因此扩大用途或混入保留评估集。
答问题 → 训判断力。即时改文档 → 训反应速度。hindsight → 训前瞻深度。
```

## 现行设计结论与验收

1. 用户先完成工作；词汇、资料、经历和判断有独立价值，不只是训练原料。方法可自然语言编辑，AGENTS.md 不是强制入口。
2. 纠正默认服务本次工作；候选发现限于已选记录/整理范围。可保留草稿、确认长期知识或仅此次，拒绝保留不影响工作。
3. 原话与系统提炼分开，来源、条件、例外、范围与版本可查；同名不自动合并，冲突不静默覆盖。
4. 沉默、收藏、批准执行、已读通知不作为偏好正例、知识确认或训练授权。明确反馈也须与评价目标和上下文匹配。
5. 知识确认、运行引用、训练授权、候选产物、评估和启用分别成立；不使用跨层的笼统“已学习”。
6. 训练由 Foundry 负责目的、授权快照、算法、产物、评估、发布、回退和撤回处理。固定反馈条数不触发自动训练或升版。
7. 系统可提出方法/标签/关系修订，用户的长期含义与本体变更走既有 proposal；共享语义由 models 管，不另建卡片数据库。
8. 执行前补上下文保留用户原话与 Secretary maker/来源；代理决定可查，不能为了顺滑伪造人类消息或扩权。
9. auto 决定推进方式，长期 grant 决定已授范围；一次批准、方法编辑、模型启用不能替代授权。统一授权文档当前缺失，由原 owner 补齐，现依 Capability/Auto 合同边界。
10. 版本 diff 是改动证据，不能自动证明用户动机或训练因果；研究数据构造与产品确认分开，研究笔记不宣称已验证性能。
11. 修订/保存失败保留草稿，另端修改展示冲突；撤回分别影响未来使用、后续训练和已有产物。来源撤权不通过缓存快照泄露内容。
12. 验收覆盖：仅此次不变长期规则、执行批准不变正例、拒绝保存仍完成任务、两项目相反判断、并发修订、撤回后默认检索排除、知识已确认但训练未授权、无改善保留现用版本。以实际资源/运行证据验收，不能用目标图或研究叙述替代。

实施依赖为 R6 DEP01–05/07；具体写入采用共享存储计划，领域未定时列出负责人和缺失合同，不用 UI-only 成功态绕开。
