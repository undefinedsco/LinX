# LinX 桌面端产品策略（Chat-first + AI-native）

## 1. 文档目标

这份文档用于收敛 LinX 桌面端的产品策略与交付纪律，避免产品一边追微信桌面版的低负担体验，一边把 AI / runtime / approval / Pod 能力直接平铺到用户面前，导致主线失焦。

本文档回答四个问题：

1. LinX 桌面端到底要“像微信”到什么程度；
2. AI 特性应该怎样融合进聊天主流程；
3. `chat / contacts / files / favorites / inbox / audit / workspace` 的信息架构应该如何收口；
4. 团队如何按渐进式开发方式交付，而不是同时暴露大量半成品。

---

## 2. 产品定位

LinX 不是纯微信克隆，也不是单纯的 AI IDE。

更准确的定位是：

- **交互骨架上接近微信桌面端**：低认知负担、聊天优先、对象直达、桌面感强；
- **能力内核上是 AI-native 工作台**：runtime、workspace、Pod 留档、审批、审计、收藏、记忆都围绕会话工作；
- **最终目标是“先像聊天应用，再显出 AI 能力”**。

一句话定义：

> 用户第一次上手觉得它像一个顺手的桌面聊天应用；第二天开始，才逐渐发现它其实是一个 AI 工作台。

---

## 3. 体验原则

### 3.1 Chat-first

- `chat` 是主舞台；
- 其他模块要尽量服务于当前会话，而不是和 `chat` 平级竞争用户注意力；
- 用户最常见的路径应该是：
  - 打开聊天；
  - 在聊天里完成大部分动作；
  - 只在需要时进入联系人、收藏、文件或设置。

### 3.2 低认知负担优先

- 不要要求用户先理解 `runtime`、`workspace`、`approval policy`、`audit` 才能开始使用；
- 这些概念必须先转译成用户能理解的交互：
  - “当前话题已绑定目录”
  - “这里需要你确认一下”
  - “这条结果已自动批准”
  - “可在右上角查看待处理事项”

### 3.3 AI 能力必须吸收到主流程

- 不是把 AI 能力做成新的页面，而是把它吸收到聊天主流程；
- 正确做法是：
  - `workspace` 成为会话能力；
  - `approval` 成为消息中的动作；
  - `inbox` 成为全局异常中心；
  - `favorites` 成为可重入的记忆索引；
  - `files` 成为会话资产面板。

### 3.4 不暴露半成品

- 半成品不要直接给用户试；
- 假按钮、mock 数据、只有 toast 的入口，都应该先收起来；
- 用户可见范围内的功能，必须至少达到：
  - 有真实主路径；
  - 没有明显的“点了没用”；
  - 有最基本的测试或烟测；
  - 可以提交、发布、回归体验。

---

## 4. 信息架构收口

### 4.1 `chat`：主舞台

`chat` 是 LinX 的默认入口，也是其他能力的挂载点。

在聊天内应该自然可见：

- 当前会话标题；
- 当前会话绑定的目录 / 仓库；
- 当前 runtime 状态；
- 当前审批策略；
- 当前待处理授权；
- 当前会话相关文件、收藏、产物的快速入口。

不应该让用户一上来就切到其他模块才能完成基本工作。

### 4.2 `contacts`：统一关系面

`contacts` 不是纯社交通讯录，也不是 AI 配置页。

它的职责是统一呈现：

- 人；
- agent；
- 群组；
- 这些对象和当前聊天体系的关系。

联系人详情页的主叙事应该仍然是：

- 这个对象是谁；
- 和我是什么关系；
- 我可以和它做什么；

而不是优先暴露模型、工具和调试信息。

### 4.3 `files`：会话资产面板

`files` 不是普通文件管理器，也不应只是 Pod 目录浏览器。

它应该统一呈现三类资产：

- 会话附件；
- workspace / runtime 产物；
- Pod 文件与导入数据。

用户心智应是：

> 这个聊天 / 工作上下文里产生或引用了哪些文件资产？

只有当 `files` 已经是“真实数据 + 真实动作”的模块时，才应放大入口。

当前最小可交付应至少满足：

- 左侧树能看到 `当前话题容器`（若已绑定 Pod 容器）与 `Pod 根目录`；
- 中间列表来自真实容器列举，而不是 mock 文件；
- 右侧详情至少支持 `打开 URI / 复制 URI / 收藏`；
- 本地 `linx://` 目录在 Web 壳不可浏览时，要明确说明限制，而不是展示假数据。

### 4.4 `favorites`：可重入的记忆索引

`favorites` 不是纯“星标列表”，也不只是微信式收藏。

它要承担：

- 记住用户认为重要的对象；
- 快速检索；
- 回到原对象；
- 回到原场景；
- 后续支持把收藏内容重新送回聊天主流程。

因此 `favorites` 的价值核心不是“看快照”，而是“重入”。

### 4.5 `inbox`：右上角全局异常中心

`inbox` 不应作为一级主导航长期存在。

推荐定位：

- 右上角 `Bell` 入口；
- 点击后打开 `Popover` 或 `Sheet`；
- 统一收口三类内容：
  - 待审批；
  - 待认证；
  - 通知 / 已完成异步结果。

原则：

- 当前会话内可就地处理的审批，优先留在 `chat` 中 inline 处理；
- `inbox` 负责汇总、补处理、历史回看；
- 不要让用户为了当前会话里的一个确认动作，频繁跳去另一个产品面。

### 4.6 `audit`：后台留痕，前台可追溯

`audit` 不应该抢占聊天主流程，也不应一开始就做成一级主导航。

它更适合：

- 作为后台持续留痕能力；
- 在相关对象详情、审批项、历史记录中按需展示；
- 在需要系统化查看时，再提供独立时间线视图。

关键不是“有一页 audit”，而是：

- 任意重要动作都能追溯；
- 任意审计记录都能回到原场景；
- 审计记录不是死日志，而是可重入的执行证据。

### 4.7 `workspace`：会话能力，不是独立宇宙

`workspace` 不应该作为漂浮概念独立存在。

用户真正理解的是：

- 这个话题绑定了哪个目录；
- 这个目录是不是仓库；
- 当前是否有运行时；
- 这个上下文里正在生成什么文件和结果。

因此：

- `workspace` 是会话能力；
- `folder / container` 是物理载体；
- 二者必须绑定建模与呈现。

## 5. Approval / Inbox 设计原则

### 5.1 审批是动作，不是系统

用户不应该先理解一套“审批系统”，再继续聊天。

正确体验是：

- 消息流中出现一张待确认卡片；
- 用户看到：
  - 请求做什么；
  - 风险是什么；
  - 可以批准 / 拒绝 / 查看差异；
- 同时该卡片在 `inbox` 中有镜像。

### 5.2 自动审批必须可配置，但不能只是裸开关

当前主流 AI 产品已经广泛提供自动审批，因此 LinX 也必须把自动审批放出来。

但产品层暴露的应该是**策略**，不是仅一个布尔值。

最小可用的策略分层：

1. **手动确认**
2. **安全操作自动通过**
3. **当前容器内自动通过**

其中：

- 会话级策略放在聊天顶部工具条；
- 全局默认策略放在设置页；
- 首次开启高风险自动审批时要弹确认提示。

### 5.3 哪些动作可自动审批

适合自动的动作：

- 只读查询；
- 当前容器内读文件；
- 当前容器内有限写入；
- 已知可信域名的低风险网络请求。

必须手动确认的动作：

- 认证；
- 密钥访问；
- 超出当前容器范围的文件操作；
- destructive 操作；
- 发布 / 推送 / 发送类动作。

### 5.4 `inbox` 与 `chat` 的边界

- `chat` 负责当前会话中的即时处理；
- `inbox` 负责全局汇总和补处理；
- 同一条审批事件可以：
  - 在聊天里 inline 显示；
  - 在 inbox 里汇总显示；
- 但其真相必须是一条共享对象，而不是前端复制两份。

## 6. Scene Restoration（场景恢复）要求

`favorites / inbox / audit` 都不能只是记录列表。

它们必须能：

- 还原回场景；
- 还原到实物；
- 还原到原始上下文。

### 6.1 `favorites`

至少支持回到：

- 原聊天；
- 原话题；
- 原消息锚点；
- 原联系人；
- 原文件详情；
- 原 workspace 相关对象。

### 6.2 `inbox`

至少支持回到：

- 触发该审批 / 认证 / 通知的聊天；
- 原审批卡片；
- 对应的 workspace / container；
- 对应对象详情。

### 6.3 `audit`

至少支持回到：

- 动作发生的 thread；
- 动作所在的 workspace / container；
- 动作指向的对象；
- 相关审批 / 输出 / 文件结果。

### 6.4 退化策略

如果原对象已经不存在：

- 退化到最近仍然存在的上层场景；
- 同时展示快照和“原对象已不存在”的提示；
- 不得只给一个失效链接。

### 6.5 当前阶段实现约束

在共享模型尚未给 `approval / audit / inbox` 补齐一等 `thread / workspace / container / about / anchor` link 前：

- `inbox / audit` 先从事件里的 `thread` 关系恢复线程；
- `workspace / container` 先通过 `Thread.workspace` 反查；
- `about` 先优先使用事件上下文或审批 `target`；
- UI 必须展示这是派生恢复链路，但不能退回成仅文本日志。

## 7. 渐进式开发与发布纪律

### 7.1 先收起，再发布

开发策略必须从“多模块同时展开”改为“逐块交付”。

规则：

- 先收起未完成内容；
- 每次只交一个可用板块；
- 达到可体验、可测试、可提交、可发布，再进入下一块。

### 7.2 发布前必须满足

一个功能板块达到“可发”至少要满足：

1. 能进入；
2. 能完成一条真实主路径；
3. 没有明显假按钮；
4. 没有依赖 mock 才能理解的核心主流程；
5. 有最基本 smoke / integration 测试；
6. 发布后团队可以真实体验。

### 7.3 未完成内容处理规则

对未完成功能，允许：

- 隐藏入口；
- 降级为只读；
- 标为内部功能；
- 放在开发模式或实验开关后面。

不允许：

- 放一个看起来可用但实际上只有 toast 的主按钮；
- 用 mock 数据冒充正式能力；
- 让用户进入半套流程后卡住。

### 7.4 建议交付顺序

#### 第 1 批：聊天主线可用

- `chat` 主路径；
- 基础 `contacts`；
- 收起骨架态 `files`；
- 收起明显未完成的联系人动作。

#### 第 2 批：收藏可重入

- `favorites` 能回到原对象；
- 收藏与聊天主线形成闭环。

#### 第 3 批：Inbox 与审批策略

- 右上角 `inbox`；
- 会话级自动审批策略；
- inline 审批卡片 + inbox 汇总镜像。

#### 第 4 批：会话资产流

- `files` 从骨架升级为真实数据；
- 打通会话附件、workspace 产物、Pod 文件。

#### 第 5 批：审计可追溯

- `audit` 可查看；
- `audit` 可回场景；
- 审批、收藏、文件、聊天之间形成闭环。

---

## 8. 对“像微信”的使用方式

LinX 对微信桌面版的借鉴，应该限定在：

- 低负担聊天壳；
- 熟悉的桌面交互；
- 对象直达；
- 文件与收藏的可重入性；
- 通知 / 右键 / 搜索 / 列表等成熟桌面模式。

LinX 不应追求：

- 把 AI 能力隐藏到完全不可见；
- 为了“像微信”而放弃 runtime / workspace / approval；
- 把所有 AI 概念都做成独立页面。

正确方向是：

> 交互像一个成熟桌面聊天产品，能力像一个 AI-native 工作台。

---

## 9. 决策摘要

### 当前明确共识

- `chat` 是主舞台；
- `workspace` 必须和 `folder / container` 结合；
- `inbox` 应降级到右上角全局入口；
- `approval` 应以 inline 卡片为主、inbox 汇总为辅；
- `favorites / inbox / audit` 都必须具备场景恢复能力；
- 未完成模块先收起，不暴露半成品；
- 开发节奏改为逐块交付、逐块发布。

### 用一句话收口

LinX 桌面端不是“把所有 AI 能力摊开给用户看”，而是：

> 先给用户一个顺手的聊天桌面端，再把 workspace、approval、inbox、audit、files、favorites 自然吸收到会话主流程里。
